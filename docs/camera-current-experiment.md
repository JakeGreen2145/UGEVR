# Current-camera ownership experiment

`Rendering.RestoreBorrowedCameraCurrent` defaults to false. Explicit activation tests whether restoring an owned `Camera.current` context after a borrowed eye pair helps desktop UI. It does not claim a native UI or fidelity fix. This supports the investigation in [screen UI issue 32](https://github.com/JakeGreen2145/UGEVR/issues/32).

The actual call path is the injector's `WaitForEndOfFrame` coroutine, `Tick`, camera/UI state scopes, two manual game-camera renders and optional isolated UI-camera renders. It does not intercept an original `OnPreCull`. Unity documents that `Camera.Render()` invokes render callbacks and image effects, and restricts normal use of `Camera.current` to render callbacks. A null current camera after a manual render is not, by itself, proof of a desktop UI defect. [Camera.Render](https://docs.unity3d.com/2019.4/Documentation/ScriptReference/Camera.Render.html), [Camera.current](https://docs.unity3d.com/2019.4/Documentation/ScriptReference/Camera-current.html).

Private saved runtime captures observed the selected game camera as current before borrowing and null after each manual game render and after ordinary camera restoration. Existing `CameraState` restores camera properties and matrices, but does not restore the current-camera context. These observations identify a state difference; they do not show which native/UI consumer depends on it.

Both actual test-game `UnityEngine.CoreModule.dll` files expose public static `void Camera.SetupCurrent(Camera)`. REA inspected their metadata without loading or executing them. ## Ownership and restoration

When enabled, a scope captures current state immediately before the camera borrow. It arms only if the selected camera is live and exactly matches the nonnull current camera. A null or foreign prior grants no restoration ownership and causes no setter call. Only the selected camera and the injector's explicitly admitted UI camera can be marked as render attempts by this scope.

After camera/UI property restoration and restored geometry rebuilding, a `finally` disposes the current scope before the existing native UI after-restoration snapshot. If current still matches the prior, no setter is needed. If current is null or exactly a UI camera actually rendered by this scope, `SetupCurrent` restores the live selected prior and a getter verifies the result. A live foreign current is preserved and reported as an ownership conflict. An admitted but unrendered UI camera is foreign for this purpose. Destroyed priors, getter/setter failures and failed verification remain explicit conflicts; they are never retried or silently guessed. The pair does not submit after an ownership conflict. Cleanup retains an earlier render exception.

Successful restoration uses three current-camera getter attempts and at most one setter. It adds no scene, component, canvas or native renderer query. Disabled scopes execute neither getter nor setter. Existing isolation, inactive-canvas and geometry guards remain in force. Scope-owned checks do not establish uninterrupted engine context or control foreign callbacks.

Overlay capture diagnostics include `currentCameraRestoration` with admission, render-attempt, getter/setter, verification and conflict fields. `desktopFidelity` always remains unknown. The ordinary native UI context snapshot records the post-restoration current camera independently. A bounded existing UI failure capture records conflicts when image diagnostics are enabled. The explicit activation log reports the experimental setting.

## Validation boundary

Controlled checks verify off-path inactivity, null/foreign admission, exact owned UI membership, foreign preservation, destruction, capture/restore/verification getter errors, setter errors and verification mismatch, render-fault cleanup order, nested owned and foreign scopes, idempotence and the after-restoration snapshot order. Both actual game-reference builds must compile. These checks model the public boundary; they do not execute Unity or prove its native behavior.

A physical probe must explicitly enable the option in a fresh owned launch, compare current-camera diagnostics and desktop/menu output, and exercise disable/re-enable and scene transitions. Native cull/clipping/alpha, layout and original game response remain independent observations. An outcome change would still need a controlled enabled/disabled comparison before attributing the desktop UI defect to this context. The 3–5 minute gameplay gate remains open.
