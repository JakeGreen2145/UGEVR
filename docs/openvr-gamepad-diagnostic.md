# Owned OpenVR-to-Input-System gamepad diagnostic

This source prototype tests explicitly selected mappings through normal Unity input updates. It is off by default. It does not establish received Windows controller buttons, original game binding consumption or a gameplay gate pass. The separate existing-keyboard E experiment remains a separate diagnostic and must be disabled for this path.

Use the existing BepInEx INI configuration:

```ini
[Input]
AllowOpenVrGamepadDiagnostic = true
DiagnosticProfile = outer-1.4.1-right-a-west-axis0-leftstick-v1
CurrentGamepadConflictPolicy = refuse
DiagnosticDurationSeconds = 15
DiagnosticDeadzone = 0.2
DiagnosticNeutralReads = 3
```

`prefer-owned` is the explicit alternative if another gamepad is current. `refuse` performs no layout registration or device creation in that case. Duration accepts 5 through 300 seconds; the window starts only after active rendered VR, game focus and the configured number of consecutive neutral valid right-controller reads. Neutral means A released and radial stick magnitude at or below the configured deadzone, so the activation sample maps to zero movement. Admission defaults to three reads and accepts 1 through 10. Each read must retain the same index, identity, runtime generation, axis source and metadata; the reader validates RightHand each time. Fault, focus loss, VR pause/disable, a held A or nonneutral axis resets admission. A valid replacement context starts a new count without creating a device early. Equal packet numbers are permitted during neutral holds; consecutive polls do not establish transport age. One window is allowed per component lifetime. Focus loss, VR disable or failure, tracked-controller loss, identity/role change, observed packet regression and runtime generation change terminate the window. After the window starts, retry requires a fresh launch. Before any window starts or owned device is created, normal VR disable or failure leaves it waiting, so a later enable can still start the already authorized first window. Component disable or game teardown cancels waiting permanently. A held button cannot arm it.

The profile polls the existing `CVRSystem` in ordinary `Injector.Update`, independently of eye count. It initializes no SDK, manifest or action set. It uses `GetControllerStateWithPose`, the actual RightHand role, a valid connected pose, bounded serial identity and verified axis-0 joystick metadata. It rechecks the role after polling. SDK `k_EButton_A`, pressed bit 7, maps to the explicitly selected gamepad button. The West profile targets original wake/interact; `outer-1.4.1-right-a-south-axis0-leftstick-v1` remains available for menu confirm/jump. Neither profile is a default general binding. Touched bits and the Index-controller button-2 alias do not substitute for bit 7. Explicit raw axis 0 maps to leftStick with a radial deadzone. Missing axis metadata or a different axis kind stays unavailable. Equal packet numbers can represent a held state; they do not prove age. Polling cannot observe a disconnect that happens completely between samples. Windows receipt of this legacy button and axis mapping requires a separate observer.

## Restricted Windows button-only profile

Select `DiagnosticProfile = outer-1.4.1-deckardmp-right-a-west-button-only-v1` explicitly for the observed test transport. The profile accepts only serial `frame_testbench_right` and model `Deckard MP`, including the space, at the current actual RightHand index. Both properties are bounded and checked again after the joint connected valid state/pose read; pose values must be finite. A neutral released A is required before arming. It maps pressed SDK A bit 7 to the same owned Gamepad West output and ignores touched bits.

This route does not query axis metadata or read/map any axis value. Left-stick output stays zero and logs report `sourceAxes=unavailable`. Unknown properties do not become a guessed joystick. The existing West and South joystick profiles retain their metadata requirements. The button-only profile can test original wake/interact; it cannot test controller movement or qualify as a general controller adapter.

The transport pin comes from the root operator's independent Windows receiver window on 2026-10-14: RightHand index 1, exact serial/model above, connected valid pose, pressed and touched mask 128 for eight of 240 reads with zero before/after. The same receiver returned UnknownProperty for all five axis-type properties. This is observed transport evidence supplied by the operator, separate from these source-only checks. PC touched128 was present despite the headset test's touchfalse request; no touch passthrough claim is made. Delivery to original game bindings and gameplay remain unvalidated.

## Restricted observed axis-0 transport profile

Select `DiagnosticProfile = outer-1.4.1-deckardmp-right-a-west-observed-axis0-leftstick-v1` explicitly to test the separately observed raw axis-0 route. It uses the same exact serial/model, role, joint valid connected pose/state and repeated identity guards as the button-only profile. SDK A pressed bit 7 maps to West. Raw received axis-0 X/Y maps to the owned left stick through the configured radial deadzone. A released and raw stick inside that deadzone are required before arming.

Only this restricted profile permits the observed `TrackedProp_UnknownProperty` result for axis-0 type metadata. A successful compatible Joystick type is also accepted. A successful conflicting type or any other property error rejects the sample before state polling. A returned integer accompanying an error is never treated as a declaration. Raw X/Y must each be finite and within [-1,1]. Logs report `sourceAxes=observed_transport_axis0`, `axis0Metadata` and a successful raw `axis0Type` or `unavailable`. They never label this route as a declared joystick. The declared joystick profiles retain their strict metadata check; button-only still queries and maps no axes.

Root's independent paired transport window on 2026-10-14 requested headset right-stick [0.35,0.60] for 500 ms, then zero. The headset read ten nonzero samples and 290 zero samples. The Windows receiver read eight raw axis-0 samples near [0.3464567,0.5984252] and 232 zero samples, with other axes zero and all axis-type properties UnknownProperty. The received values are consistent with 44/127 and 76/127 quantization, rather than exact passthrough. The injector uses the received values. This point and neutral return do not establish unobserved signs, full range, latency, every controller model or original movement consumption. These source checks validate filtering, radial output and cleanup independently of the operator's transport evidence.

## Ownership and compatibility

The backend queues public `GamepadState` events only to a separately owned `Gamepad`. It never changes physical keyboard state, nonowned keys, IME, physical controller input, device enable state or game input actions. No Lua, native virtual-controller driver or Frame Testbench dependency is introduced.

The explicitly selected Outer compatibility profile accepts only the inspected game assembly MVID `995fa289-c662-4f44-9176-33f00ebf2052` and the loaded Input System 1.4.1 MVID `eb31f34a-975f-46d1-9e8a-f468772f04b5`. A missing/mismatched assembly makes input unavailable without failing VR or loading another assembly. This is a build-specific compatibility boundary, not a claim of generic Unity input support.

The profile registers a unique `XInputControllerWindowsUGEVR_<guid>` layout extending the public `Gamepad` layout. Its interface is a unique UGEVR identifier, its manufacturer is `UGEVR`, its product explicitly says synthetic diagnostic gamepad and its serial starts with `ugevr-synthetic-`. Capabilities are `{}`. It supplies no physical vendor/product IDs or physical serial. Public matcher JSON has no serial field, so the matcher uses the unique synthetic interface instead. Registration cannot match existing hardware through a broad XInput or HID interface.

The inspected original Outer code accepts device names starting with `XInputControllerWindows`. This compatibility rule is isolated in `OuterGamepadCompatibilityProfile`, rather than applied as a general binding default. It permits the honest synthetic device to use the game's standard gamepad compatibility branch. The native Windows XInput layout uses internal `XINP` state, which cannot simply accept public `GPAD` events. This prototype therefore uses a public derived Gamepad layout with GPAD state. It does not generate runtime code or access the private XInput state type.

Creation captures the exact owned device reference during the synchronous public Added callback and verifies the returned reference. This permits cleanup after an add call creates the device and then throws. A failure without a captured identity is reported as an unknown add outcome; it does not guess a device to delete. Queue calls that throw still trigger release attempts because they may already have queued input. Removal operates only on the captured reference.

The backend samples `Gamepad.current` before mutation and before nonneutral queues. An observed external takeover stops the window. After removal, the previous current is restored only through public `MakeCurrent` if it remains added and enabled, no takeover was observed and current is still null. An external current selected during removal is preserved. These are synchronous observation guards, not an atomic guarantee against all other scripts or input events. Already queued normal input can affect current selection before a later Update detects a conflict. Explicit `prefer-owned` accepts the diagnostic's normal current-device selection while active.

Release queues neutral state and normally waits for a later Update to observe neutral state on the owned device. Teardown and observed current conflicts attempt release and remove immediately. In those cases, queued neutral processing is not claimed. Removal unbinds actions from the removed device through the normal public API. Cleanup has at most two release attempts and two removal attempts. If the SDK or Unity stops returning, these deadlines cannot preempt its native call or run after process teardown.

Layout ownership includes the unique name, a recorded public layout definition, public layout-change observation and a bounded 256-device check. A collision is refused before registration. A replaced layout or any other device using it prevents deregistration. Such a layout is preserved and reported. Layout/device callbacks are unsubscribed after successful bounded cleanup. An unavailable cleanup remains explicit; no original device or global input state is cleared to compensate.

`INPUT_DIAGNOSTIC` log records show selected profile, axis source/metadata, admission counts and status/reason, creation and queue counts, observed owned state samples, release/removal attempts and cleanup/current restoration outcomes. Observed owned state is read through public unprocessed stick state; normal game processors can alter the values the game consumes. The queue itself is not a processing acknowledgement. `nativeUnavailableReason` retains the last nonempty source-failure category across valid samples and cleanup. A later source failure replaces the earlier category, so the failure that ends an active window remains visible. Reader categories distinguish SDK state-read failure, disconnected/invalid/nonfinite pose, observed role or pinned identity change, axis faults and ordinary managed reader exception type. Exceptions are categorized by type without parsing messages; process failure and blocking native calls remain outside this handler. These diagnostics do not relax any guard or restart a completed window. All records keep `gameConsumption=unknown`.

## Private identity-result diagnostics

`Input.CaptureIdentityDetails` defaults to false. Explicit activation writes bounded private YAML under the controller-owned session's `UnityVR-evidence` directory. Seven periodic property snapshots and one reserved first successful read form the eight-record budget, with one additional reserved terminal snapshot. Polls with no attempted serial/model property do not spend periodic records, so a disconnected controller cannot exhaust the budget before its first real identity result. The first success and terminal result can be captured immediately; other attempts are limited to the existing one-second report cadence. Files use CreateNew and are never overwritten. Each is capped at 16384 bytes; each raw property value is capped at 256 characters with an explicit truncation marker.

Snapshots record initial and post-state serial/model raw text, SDK error name/code, required byte count, requested buffer bytes, builder length and initial/returned builder capacity. They also record selected and post-state device index, class and role. Both properties are captured before each identity validation, even when the serial disagrees. A thrown call has `returned: false`, no fabricated required-byte result and its exception type; the error reference is still recorded but is not a completed SDK result. Empty text, zero required bytes, property errors, size rejection and identity disagreement remain distinct observations. All original primary guards and exact identity pins remain enforced. A terminal failure snapshot survives neutral release, Complete and later valid samples.

Normal input logs expose stage/verdict and bounded capture attempt/error status without raw IDs. Raw snapshot files are private device evidence and must be redacted from public issue reports. The distribution excludes evidence files. These diagnostics do not establish why a property result differs across processes.

The pinned SDK source commit is `0924064316de3effbcd1acf1e309182a2deb1c05`. Its C++ `GetStringTrackedDeviceProperty` returns the necessary byte count including the trailing NUL and takes `char*`, byte buffer size and an error pointer. The generated C# delegate uses StdCall, uint results, StringBuilder and a ref error enum, with no explicit string MarshalAs or charset annotation. The vendored binding is unchanged. The independent Windows probe uses capacity/size 256 and permits needed-zero with text; this injector uses 257 and rejects needed-zero. Those are source differences to compare with actual results, not a demonstrated cause. No secondary capacity-256 comparison is added in this patch. Controlled .NET fixture behavior does not establish Unity Mono marshaling behavior.

## Source evidence and remaining test

The shipped Input System artifact has SHA256 `e5eb042f7a120f3135844519bf8e3114a81da4e3c35cddeceff528a13d6bdfd7`. REA metadata record `ev_7fb98fa575ac70da612842fb0f5386ecb05da3bf9e99b3db05f44113d65d8fc1` identifies public RegisterLayout JSON at `0x0600031b`, AddDevice description at `0x06000339`, RemoveDevice at `0x0600033b`, QueueStateEvent at `0x0600035d`, Gamepad.current at `0x06000469`, Gamepad.MakeCurrent at `0x0600046d`, public `ReadUnprocessedValue` at `0x060003c4` and GPAD state fields. The selected public button getters are South `0x06000446` and West `0x06000442`; the public enum literals are South `0x040004d4`, value 6, and West `0x040004d5`, value 7. Production pins both the selected getter and literal/value. OpenVR A bit 7 and Input System West bit 7 belong to separate enums; the backend resolves the selected public enum, rather than sharing a mask. Controlled tests use a different West bit to check that distinction. Broader metadata coverage is partial for unrelated generic signatures; runtime validation checks the selected public shapes and pinned method/field tokens. Controlled tests bypass build-local tokens only for their fake public API fixture. Production factory identity checks remain enabled.

The shipped Outer game artifact has SHA256 `0ef96f7ff2c37ff95012bb881c760c28e0fa2f60731945c61b7cc6b30deace87`. REA record `ev_dc559f0480035bed921e319ee6bcbee7855102230994c489faa2c19a938449cf` plus complete read-only CIL decoding identify `InputUtil.IsXInputController` at `0x06000d1e` as a name-prefix test. `GetEnableDeviceWhitelistIds`, `0x06000d1c`, includes vendor 1118/product -1. `ProcessGamepadThroughWhitelist`, `0x06000f6f`, reads description capabilities, then selects that compatibility ID for the standard prefix before checking the whitelist. Otherwise it can call public DisableDevice. The prototype never re-enables a game-disabled device.

The shipped `resources.assets` has SHA256 `d1bd4b9d0bd8479e29c16b35169c8fea044927925d381eca7c8b2d5acb980a03`. Its `OWInputCommands` InputActionAsset is object 3982, offset 22258768, size 30080. Read-only UnityPy decoding with the shipped class metadata and Unity 2019.4.39f1 consumes the full object. `Interact/interact` binds `<Gamepad>/buttonWest` and `<Keyboard>/e`. `Movement/moveX` binds the left-stick horizontal directions and `Movement/moveZ` binds its vertical directions. `Movement/jump` and `Menu/menuConfirm` use `<Gamepad>/{PrimaryAction}`. The original wake branch in `PlayerCameraEffectController.Update`, `0x0600033b`, reads `InputLibrary.interact` at IL 40 and `OWInput.IsNewlyPressed` at IL 46 before invoking its normal wake behavior. Therefore South is not the source-backed wake binding.

The Windows game's `InputManager.ActiveUser` public field, `0x040012e7`, has no decoded CIL reads or writes in this assembly. `RefreshConnectedDevices`, `0x06000f6d`, and `TitleButtonPrompt.OnUnpairedDeviceInput`, `0x06000850`, return without work. The title enables public unpaired activity listening and forwards its callback, but this handler does not pair a device. The shipped game references no public InputUser pairing or action-association method.

The game still exposes an input-asset device filter. `SetPairedDeviceExclusive`, `0x06000f77`, passes one device to its input manager; `InputCommandManager.ModifyInputAssetDeviceList`, `0x06000f2c`, disables the asset, sets its devices and re-enables it. No concrete game caller reaches the exclusive method in the decoded assembly, and the asset setter appears only in this filter wrapper. The injector calls neither method. Runtime filters or saved binding overrides can still exclude an added gamepad. No InputUser pairing change is made without evidence it is needed. Root must observe the legacy Windows button and axis, owned device state, resolved original action controls and the normal game's wake/movement response. Neither source compatibility nor a successful add proves consumption.

Public API behavior is documented in the [Input System 1.4.1 source](https://github.com/Unity-Technologies/InputSystem/blob/1.4.1/Packages/com.unity.inputsystem/InputSystem/InputSystem.cs), [Gamepad source](https://github.com/Unity-Technologies/InputSystem/blob/1.4.1/Packages/com.unity.inputsystem/InputSystem/Devices/Gamepad.cs) and the pinned [OpenVR header](https://github.com/ValveSoftware/openvr/blob/master/headers/openvr.h). The first gate still requires observed original game response and cleanup, followed by its accepted 3 to 5 minutes of play.
