# Unity frame transport requirements

Research for [What do OpenVR and OpenXR require for Unity frame, texture, depth, and lifecycle transport?](https://github.com/JakeGreen2145/UGEVR/issues/19), completed 2026-10-13. This report establishes API contracts and identifies checks for the later runtime/GPU decision. It chooses no architecture and reports no new runtime experiment.

## Pose and frame identity

OpenVR scene applications obtain render poses with `WaitGetPoses` immediately before rendering. The optional game-pose array predicts an additional frame ahead, so it is not interchangeable with the render-pose array. `GetLastPoses` retrieves the preceding wait's poses. `Submit` rejects a second submission for the same eye before another `WaitGetPoses`. The SDK also exposes `GetLastPosePredictionIDs`, whose differences count headset vsync intervals. These IDs can identify a rendered frame more reliably than Unity's game-frame counter alone. When rendering uses a different pose, `VRTextureWithPose_t` and `Submit_TextureWithPose` convey the pose actually used. [OpenVR header](https://github.com/ValveSoftware/openvr/blob/0924064316de3effbcd1acf1e309182a2deb1c05/headers/openvr.h#L3658-L3702), [pose/depth structures](https://github.com/ValveSoftware/openvr/blob/0924064316de3effbcd1acf1e309182a2deb1c05/headers/openvr.h#L173-L194), [prediction IDs](https://github.com/ValveSoftware/openvr/blob/0924064316de3effbcd1acf1e309182a2deb1c05/headers/openvr.h#L3872-L3877).

OpenXR separates pacing, frame start and submission into `xrWaitFrame`, `xrBeginFrame` and `xrEndFrame`. `xrWaitFrame` supplies a monotonically increasing predicted display time and a predicted period. The specification recommends one consistent target display time throughout a generated frame. Locate the views for that time, preserve the poses and FOV actually used, and submit them with the frame's display time. Repeating `xrLocateViews` for the same time can return improved predictions, so identical timestamps do not guarantee identical matrices. If the injector late-updates the view, its submitted metadata must describe that updated rendering. This last sentence is an implementation implication of the contract. [Frame synchronization and submission](https://github.com/KhronosGroup/OpenXR-Docs/blob/5a82d45bc9e0adbaa24b6c4a3e5b6d50e08c887d/specification/sources/chapters/rendering.adoc#L764-L1053), [view location](https://github.com/KhronosGroup/OpenXR-Docs/blob/5a82d45bc9e0adbaa24b6c4a3e5b6d50e08c887d/specification/sources/chapters/rendering.adoc#L577-L691).

`xrWaitFrame` may run on a different thread from begin/end, but concurrent waits require application synchronization. Begin/end on separate threads also require synchronization. `XR_FRAME_DISCARDED` and `XR_TIMEOUT_EXPIRED` are success-class statuses with specific behavior, not permission to treat every nonnegative return as a usable image or ordinary completed frame. [Frame rules](https://github.com/KhronosGroup/OpenXR-Docs/blob/5a82d45bc9e0adbaa24b6c4a3e5b6d50e08c887d/specification/sources/chapters/rendering.adoc#L764-L974), [image wait rules](https://github.com/KhronosGroup/OpenXR-Docs/blob/5a82d45bc9e0adbaa24b6c4a3e5b6d50e08c887d/specification/sources/chapters/rendering.adoc#L456-L494).

Both APIs supply full per-view transforms. OpenVR `GetEyeToHeadTransform` is a transform, not merely an IPD offset. OpenXR projection views carry orientation as well as position and FOV. An injector that ignores per-eye rotation assumes parallel eyes. That assumption needs an explicit check on canted displays. Both APIs use right-handed coordinates and meters; changing basis for Unity must transform positions and rotations consistently. [OpenVR coordinates and eye transform](https://github.com/ValveSoftware/openvr/blob/0924064316de3effbcd1acf1e309182a2deb1c05/headers/openvr.h#L36-L45), [OpenVR system](https://github.com/ValveSoftware/openvr/blob/0924064316de3effbcd1acf1e309182a2deb1c05/headers/openvr.h#L2363-L2366), [OpenXR coordinates](https://github.com/KhronosGroup/OpenXR-Docs/blob/5a82d45bc9e0adbaa24b6c4a3e5b6d50e08c887d/specification/sources/chapters/fundamentals.adoc#L1240-L1267), [projection views](https://github.com/KhronosGroup/OpenXR-Docs/blob/5a82d45bc9e0adbaa24b6c4a3e5b6d50e08c887d/specification/sources/chapters/rendering.adoc#L1340-L1384).

## Unity scheduling and GPU ownership

Unity scripts can execute on a different thread from graphics commands. `GL.IssuePluginEvent` queues a native callback on the render thread. A callback queued after a camera render is ordered within that rendering pipeline; it does not alone prove that the GPU has completed its work. `UnityPluginLoad` and the interface registry provide native graphics access and device-event callbacks. A manually injected DLL must establish that it receives those interfaces; ordinary DLL loading is not evidence that Unity registered a native plugin. [Unity native plugin documentation](https://docs.unity3d.com/2022.3/Documentation/Manual/NativePluginInterface.html).

`GetNativeTexturePtr` returns a graphics resource pointer, including `ID3D11Resource` or `ID3D12Resource`. Unity warns that modifying texture data can change the pointer and that querying it during multithreaded rendering synchronizes the render thread. This supports pointer-refresh requirements but does not promise GPU completion or compositor ownership. D3D11 `Flush` submits buffered commands asynchronously; a successful return is not a GPU-completion fence. [Unity native pointer documentation](https://docs.unity3d.com/2022.3/Documentation/ScriptReference/Texture.GetNativeTexturePtr.html), [Microsoft Flush contract](https://learn.microsoft.com/en-us/windows/win32/api/d3d11/nf-d3d11-id3d11devicecontext-flush).

Unity's versioned D3D12 interfaces expose different capabilities. Newer interfaces provide the command queue, frame fence, direct command-list execution with expected/post resource states, and event configuration. The interface header requires use on the rendering/submission thread. `graphicsQueueAccess=Allow` excludes Unity worker-thread access to that queue during the event. Separate flags request command-buffer flushes and worker synchronization. Copying the latest header does not establish that an older game implements its GUID. Interface discovery must precede choosing its path. [Pinned Unity D3D12 header](https://github.com/Unity-Technologies/NativeRenderingPlugin/blob/522254181faf188efa8b50c3e3bf6fce720b26e4/PluginSource/source/Unity/IUnityGraphicsD3D12.h), [Unity D3D12 example](https://github.com/Unity-Technologies/NativeRenderingPlugin/blob/522254181faf188efa8b50c3e3bf6fce720b26e4/PluginSource/source/RenderAPI_D3D12.cpp).

OpenVR's D3D11 `WaitGetPoses` records a GPU timestamp. The header explicitly documents that behavior; it does not state a universal requirement that all OpenVR waits run on Unity's render thread. Putting it there is a defensible way to serialize access to Unity's context. Explicit timing is available for Vulkan/D3D12 and requires `SubmitExplicitTimingData` immediately before the frame's first queue submission. The documented queue-isolation guarantee for explicit application handoff concerns Vulkan. It should not be broadened into an unverified blanket D3D12 thread-safety guarantee. [OpenVR explicit timing contract](https://github.com/ValveSoftware/openvr/blob/0924064316de3effbcd1acf1e309182a2deb1c05/headers/openvr.h#L3818-L3845).

## Texture transport differs by API

| Path | Contract | Unity consequence |
| --- | --- | --- |
| OpenVR/D3D11 | `TextureType_DirectX` carries the D3D11 texture. Submit can reject a wrong adapter, unsupported sharing format or invalid texture. | Validate the actual device, resource type, sample/format layout and current pointer before submission. |
| OpenVR/D3D12 | `TextureType_DirectX12` carries `D3D12TextureData_t`, with resource, queue and node mask. Valve's wiki requires `PIXEL_SHADER_RESOURCE` before submission and leaves it there afterward. Shutdown precedes destruction of those resources. | A D3D12 resource pointer cannot be submitted as the D3D11 handle. Track source state, use the correct queue, then restore Unity's expected state. |
| OpenXR/D3D11 | Graphics requirements specify the adapter LUID and minimum feature level. The session binds a compatible D3D11 device; the runtime owns its swapchain textures. | Verify Unity's device meets runtime requirements. Render or copy into runtime-provided images rather than submitting arbitrary Unity textures. |
| OpenXR/D3D12 | The session binds device and queue. Successful image wait makes color images available as `RENDER_TARGET`, depth as `DEPTH_WRITE`, on that queue. Release requires these states and queue availability again. | Transition through copy states if copying, submit the copy, restore required states before release, and order cross-queue work explicitly. |

Sources for the table are the [OpenVR handle/submit contracts](https://github.com/ValveSoftware/openvr/blob/0924064316de3effbcd1acf1e309182a2deb1c05/headers/openvr.h), [Valve D3D12 guidance](https://github.com/ValveSoftware/openvr/wiki/DirectX12), [OpenXR D3D11 extension](https://github.com/KhronosGroup/OpenXR-Docs/blob/5a82d45bc9e0adbaa24b6c4a3e5b6d50e08c887d/specification/sources/chapters/extensions/khr/khr_d3d11_enable.adoc) and [OpenXR D3D12 extension](https://github.com/KhronosGroup/OpenXR-Docs/blob/5a82d45bc9e0adbaa24b6c4a3e5b6d50e08c887d/specification/sources/chapters/extensions/khr/khr_d3d12_enable.adoc).

OpenXR image acquisition returns an index; it does not make the image writable. Each acquire requires a successful image wait before GPU writes. A timeout leaves the same oldest acquired image pending. Commands referencing the image must be submitted before release. `xrEndFrame` references the most recently released image from each swapchain. Select formats through enumeration and declare usage flags that permit the actual rendering/copy operations. The runtime interprets D3D images with a top-left origin. [OpenXR swapchain lifecycle](https://github.com/KhronosGroup/OpenXR-Docs/blob/5a82d45bc9e0adbaa24b6c4a3e5b6d50e08c887d/specification/sources/chapters/rendering.adoc#L60-L575), [D3D11 origin/usage](https://github.com/KhronosGroup/OpenXR-Docs/blob/5a82d45bc9e0adbaa24b6c4a3e5b6d50e08c887d/specification/sources/chapters/extensions/khr/khr_d3d11_enable.adoc).

OpenXR composition uses linear color values. An sRGB format signals conversion; other formats are treated as linear. OpenVR separately specifies color space in `Texture_t`. A successful submit does not verify correct gamma, alpha, orientation, eye selection or MSAA resolution. Those require image checks. [OpenXR color rules](https://github.com/KhronosGroup/OpenXR-Docs/blob/5a82d45bc9e0adbaa24b6c4a3e5b6d50e08c887d/specification/sources/chapters/rendering.adoc#L21-L50), [OpenVR texture structure](https://github.com/ValveSoftware/openvr/blob/0924064316de3effbcd1acf1e309182a2deb1c05/headers/openvr.h#L149-L162).

## Depth, layers and lifecycle

OpenXR depth is optional extension functionality. `XR_KHR_composition_layer_depth` associates projected depth with every projection view through its `next` chain. `minDepth < maxDepth` remains required within [0,1]. Reversed depth is expressed with `nearZ > farZ`, not reversed min/max values. Distances are positive meters, may include infinity, and must differ. The runtime may use depth for reprojection; the extension does not guarantee a particular reprojection result. OpenVR depth uses a handle, projection matrix and depth range with the matching submit flags. Correct depth requires matching the color frame, projection, coordinate conversion and physical scale. [OpenXR depth specification](https://github.com/KhronosGroup/OpenXR-Docs/blob/5a82d45bc9e0adbaa24b6c4a3e5b6d50e08c887d/specification/sources/chapters/extensions/khr/khr_composition_layer_depth.adoc), [OpenVR depth structures/flags](https://github.com/ValveSoftware/openvr/blob/0924064316de3effbcd1acf1e309182a2deb1c05/headers/openvr.h#L179-L194).

Unity documents reversed Z on D3D11/D3D12. `Camera.projectionMatrix` and the GPU-adjusted projection are different representations. `GL.GetGPUProjectionMatrix` accounts for backend conventions; inspect `SystemInfo.usesReversedZBuffer` and the actual depth resource before exporting it. A linearized depth texture cannot be substituted for projected depth without an explicit conversion. [Unity shader platform conventions](https://docs.unity3d.com/2022.3/Documentation/Manual/SL-PlatformDifferences.html), [OpenXR projected-depth requirement](https://github.com/KhronosGroup/OpenXR-Docs/blob/5a82d45bc9e0adbaa24b6c4a3e5b6d50e08c887d/specification/sources/chapters/extensions/khr/khr_composition_layer_depth.adoc#L120-L147).

OpenXR projection and quad layers are core mechanisms. Every frame must resubmit the layers to display, even when an image remains unchanged. Layer order, space, alpha flags, image rectangle and array index form part of submission. Extra layer types and depth require runtime extension discovery. OpenVR scene eyes and overlays are distinct interfaces; an overlay is not a substitute for a stereo scene submission. [OpenXR composition layers](https://github.com/KhronosGroup/OpenXR-Docs/blob/5a82d45bc9e0adbaa24b6c4a3e5b6d50e08c887d/specification/sources/chapters/rendering.adoc#L1130-L1443), [OpenVR compositor and overlay interfaces](https://github.com/ValveSoftware/openvr/blob/0924064316de3effbcd1acf1e309182a2deb1c05/headers/openvr.h).

OpenXR starts the session on `READY`, stops the frame loop and ends the session on `STOPPING`, and can destroy/recreate on `LOSS_PENDING`. `EXITING` calls for ending the XR experience without automatic restart. `VISIBLE` permits continued rendering without input focus; `FOCUSED` permits XR input. If `shouldRender` is false, continue the running frame loop but omit heavy rendering and layers. Invalid view-state flags prohibit using invalid pose fields. Reference-space changes also need handling. These are distinct from Windows foreground focus and from a Unity scene/camera transition. [Session state specification](https://github.com/KhronosGroup/OpenXR-Docs/blob/5a82d45bc9e0adbaa24b6c4a3e5b6d50e08c887d/specification/sources/chapters/session.adoc), [view validity and shouldRender](https://github.com/KhronosGroup/OpenXR-Docs/blob/5a82d45bc9e0adbaa24b6c4a3e5b6d50e08c887d/specification/sources/chapters/rendering.adoc#L710-L907), [reference spaces](https://github.com/KhronosGroup/OpenXR-Docs/blob/5a82d45bc9e0adbaa24b6c4a3e5b6d50e08c887d/specification/sources/chapters/spaces.adoc).

OpenVR reports lack of scene focus through wait/submit errors. The pinned header documents throttled waits on loss of focus and requires `PostPresentHandoff` after the companion-window Present, on the rendering thread, if used. Runtime quit events and device changes need event handling. Neither API promises that an injector can continue using stale session/device/texture objects after a runtime restart. Recovery policy remains a decision. [OpenVR compositor contracts](https://github.com/ValveSoftware/openvr/blob/0924064316de3effbcd1acf1e309182a2deb1c05/headers/openvr.h#L3658-L3710), [OpenVR events](https://github.com/ValveSoftware/openvr/blob/0924064316de3effbcd1acf1e309182a2deb1c05/headers/openvr.h).

## What the existing POC establishes

The pinned [managed injector](https://github.com/JakeGreen2145/UGEVR/blob/6f84686187025e1e9d2968f61d5713f0d006b905/src/Injector.cs) queues a render-thread wait, synchronizes through a texture-pointer query, reads last render poses, renders two eyes on the original camera, restores it and refreshes pointers before queuing submit. The [native bridge](https://github.com/JakeGreen2145/UGEVR/blob/6f84686187025e1e9d2968f61d5713f0d006b905/src/RenderBridge.cpp) submits D3D11 textures with reversed vertical bounds and counts successful pairs. It omits `PostPresentHandoff`, relying on a later wait. These are source facts, not general API guarantees.

The [published validation artifact](https://github.com/JakeGreen2145/UGEVR/blob/6f84686187025e1e9d2968f61d5713f0d006b905/docs/validation.json) reports 14 simulated-driver pose checks for Firewatch and Outer Wilds, camera restoration, about 64 mm eye separation and nonidentical eye images. The [README](https://github.com/JakeGreen2145/UGEVR/blob/6f84686187025e1e9d2968f61d5713f0d006b905/README.md) qualifies this as simulated-headset evidence. This research inspected those published results; it did not rerun them or establish physical latency, comfort, gameplay stability or broad pipeline compatibility.

Static gaps in the POC are concrete:

- It uses eye-to-head translation but assigns the same head rotation to both cameras. It discards eye rotation, so nonidentity canted-eye transforms are not faithfully composed.
- Its wait callback discards `WaitGetPoses`' return code. Managed code checks pose validity but does not manage scene-focus/quit/device events.
- Shared raw texture pointers have no explicit frame descriptor or lifetime protocol; correctness relies on its current serial query/event behavior. It has no pose-prediction ID trace.
- It casts pointers to D3D11 textures without selecting or rejecting another graphics backend. There is no OpenXR or D3D12 implementation.
- It submits color only and does not validate depth, color encoding or composited layers.
- Shutdown occurs on application quit. Runtime restart, native-device replacement and texture teardown are not a state machine.

These gaps are derived from the cited source. They do not invalidate its two-game software POC; they limit the claims that can be generalized from it.

UEVR's pinned [OpenXR runtime](https://github.com/praydog/UEVR/blob/4ee5c6b6162dee2291fc75f9dfc57667f6d45a2d/src/mods/vr/runtimes/OpenXR.cpp) tracks frame synchronization, locates views and submits projection/depth data. Its [D3D12 component](https://github.com/praydog/UEVR/blob/4ee5c6b6162dee2291fc75f9dfc57667f6d45a2d/src/mods/vr/D3D12Component.cpp) has explicit copy/state handling. That code confirms the feature audit has concrete implementations to study. Runtime workarounds or choices such as its near/far depth values are examples to examine, not guarantees to copy into Unity unchanged.

## Alternatives for the human decision

One option renders into Unity-owned eye targets and then copies or resolves into OpenXR images at a native callback. It preserves Unity's ordinary target ownership but adds copy cost and requires ordered source/image lifetime and state tracking. Another wraps runtime images as external Unity targets. It can avoid a copy but requires proof that each Unity version/backend can wrap the resource and render into it during the acquired interval without destroying runtime ownership. A third uses native interception where supported plugin interfaces are unavailable. It requires separate evidence for command ordering, device access and compatibility. These are engineering deductions from the ownership contracts, not selected designs.

Scheduling can use a deliberately synchronized single frame initially or a pipeline that passes an immutable descriptor through main, render and GPU submission stages. That descriptor could record runtime generation, target time/prediction ID, poses/FOV, texture generation, resource states and queue/fence ownership. Pipelining promises no measured benefit here and must retain the frame contract. The human ticket should choose tradeoffs after prototypes establish which mechanisms are present in representative games.

## Falsifiable checks before a compatibility claim

1. Log runtime generation, target time/prediction ID, both eye matrices and texture generation through render and submit. Artificially delay one stage. Reject cross-frame pairs, duplicate-eye submissions and stale textures.
2. Use asymmetric eye markers and known near/far geometry. Compare runtime poses against each rendered eye, including synthetic nonidentity eye rotations, then verify a physical canted headset if claimed.
3. For every runtime/backend path, log adapter LUID, device/queue identity, format, samples and resource state. Force an incompatible configuration and require a clear failure rather than a bad cast or black image.
4. On OpenXR, force image-wait timeout, skipped render and discarded frame. Check that call order remains legal, images are not written before wait succeeds, and all submitted GPU work precedes release.
5. On D3D12, use API validation and capture resource barriers. Verify OpenXR images return to `RENDER_TARGET`/`DEPTH_WRITE`, OpenVR images meet its documented shader-resource state, and Unity's state tracker agrees after the event.
6. Check calibrated gamma, top/bottom orientation, alpha and sample resolve in each eye. Depth checks should compare encoded projected depth with the actual GPU projection and meter scale, including reversed Z.
7. Exercise dashboard/focus loss, headset sleep/disconnect, camera and scene changes, target recreation, runtime shutdown/restart and game exit. Check resource teardown only after relevant in-flight work is safe, and distinguish deliberate exit from recoverable session loss.
8. Measure CPU waits, GPU durations, prediction age, dropped/reprojected frames and stream transport separately. A successful compositor return or desktop screenshot does not prove photons reached the headset.

The user's proposed 3-5 minute first gameplay gate can include short targeted sequences for these checks. Duration and passing thresholds belong to the validation decision. Steam Frame testbench extensions still need to establish launch of streamed games and observation of the physical display/transport; this report makes no claim that those facilities already exist. Automated pose and frame traces supplement physical-headset evidence and do not replace it.
