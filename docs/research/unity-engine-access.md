# Shipped Unity player bootstrap and engine access

Research for [Which public mechanisms can bootstrap and inspect shipped Mono and IL2CPP Unity players?](https://github.com/JakeGreen2145/UGEVR/issues/17). Investigated 2026-10-13. This report records mechanisms and experiments for later architecture decisions. No game was launched, loader installed, or compatibility cell validated during this research.

## Findings that affect the next decisions

Public loaders provide concrete routes into both Mono and IL2CPP Windows players. Mono can execute an added assembly in the game's existing runtime. IL2CPP needs native calls or a separate managed runtime plus generated interop. These routes have different initialization, metadata and lifetime requirements. Neither route establishes that a particular game's camera or rendering path can produce correct VR output. The [Doorstop runtime description](https://github.com/NeighTools/UnityDoorstop/blob/3035af7ae73ed071200c995886264d62ceb3488b/README.md) and [BepInEx IL2CPP project dependencies](https://github.com/BepInEx/BepInEx/blob/5b766a3b7f6c164d4798924a93f3acf4db769d06/Runtimes/Unity/BepInEx.Unity.IL2CPP/BepInEx.Unity.IL2CPP.csproj) establish these mechanisms.

Stripping is a capability question per method and per native module. A missing generated wrapper, missing runtime metadata, unavailable AOT body and missing native engine implementation are different failures. A wrapper generator can restore some managed Unity method bodies or bindings from matching reference assemblies. It cannot recreate native engine code that the publisher removed. Unity documents both [managed stripping](https://docs.unity.com/en-us/engine/6000.3/manual/scripting/compilation-and-code-reload/script-compilation/managed-code-stripping/unity-linker) and [native engine stripping](https://docs.unity3d.com/ja/current/ScriptReference/PlayerSettings-stripEngineCode.html). Interop's [method restoration pass](https://github.com/BepInEx/Il2CppInterop/blob/81a6f78c8b653e0da4a3420ac4cd00819e8b6292/Il2CppInterop.Generator/Passes/Pass80UnstripMethods.cs) shows what it actually attempts to restore.

Runtime thread registration does not dispatch work to Unity's main thread. Main-thread engine calls and render-thread graphics work need separate scheduling. Unity's documented [plugin event mechanism](https://docs.unity3d.com/2017.4/Documentation/ScriptReference/GL.IssuePluginEvent.html) already exists in the 2017.4 generation and still exists in [current documentation](https://docs.unity.com/en-us/engine/6000.6/script-reference/unityengine/gl/issuepluginevent). This is evidence of that API's longevity, not evidence that every stripped player retains it.

## Startup loading versus attachment

On Windows, Doorstop's [entrypoint code](https://github.com/NeighTools/UnityDoorstop/blob/3035af7ae73ed071200c995886264d62ceb3488b/src/windows/entrypoint.c) loads the real proxy DLL and installs IAT hooks. It hooks `GetProcAddress` in `UnityPlayer.dll`, or the executable if there is no separate UnityPlayer module. It redirects resolution of runtime initialization functions including `mono_jit_init_version` and `il2cpp_init`.

The [bootstrap implementation](https://github.com/NeighTools/UnityDoorstop/blob/3035af7ae73ed071200c995886264d62ceb3488b/src/bootstrap.c) calls the real runtime initializer before its managed bootstrap. On Mono it opens the assembly and invokes `Doorstop.Entrypoint.Start` in the existing domain. On IL2CPP it loads CoreCLR, creates a delegate for that entrypoint and invokes it after the real `il2cpp_init` returns. The early runtime entrypoint is distinct from the point where Unity objects are safe to create.

BepInEx then provides another readiness gate:

- Its inspected [Mono entrypoint patcher](https://github.com/BepInEx/BepInEx/blob/5b766a3b7f6c164d4798924a93f3acf4db769d06/Runtimes/Unity/BepInEx.Unity.Mono.Preloader/EntrypointPatcher.cs) injects a call to `UnityChainloader.StaticStart`. Defaults select `UnityEngine.dll` before Unity 2017, otherwise `UnityEngine.CoreModule.dll`; the default type is `MonoBehaviour` before Unity 5 and `Application` thereafter. The method default is `.cctor`. The configured type and method must exist or be creatable by that patcher. Once the chainloader initializes, it creates a persistent manager GameObject and adds plugin components. [Chainloader source](https://github.com/BepInEx/BepInEx/blob/5b766a3b7f6c164d4798924a93f3acf4db769d06/Runtimes/Unity/BepInEx.Unity.Mono/Bootstrap/UnityChainloader.cs).
- Its inspected [IL2CPP chainloader](https://github.com/BepInEx/BepInEx/blob/5b766a3b7f6c164d4798924a93f3acf4db769d06/Runtimes/Unity/BepInEx.Unity.IL2CPP/Il2CppChainloader.cs) detours exported `il2cpp_runtime_invoke`. It executes plugins when it observes the method name `Internal_ActiveSceneChanged`, then removes the detour. Failure to load the native game assembly, resolve the export or observe that readiness callback is a loader failure to diagnose. A plugin `Load` message alone does not prove recurring Unity callbacks work.

This source path is designed around future runtime initialization and readiness events. Loading Doorstop after those events have already happened does not retroactively replay them. This is an inference from the hooks, not a tested late-attachment result. Doorstop's debugger attachment guidance describes attaching a debugger to code already bootstrapped by Doorstop; it is not an arbitrary managed plugin attachment API.

Late attachment is a separate experiment. On Mono, native code can locate the existing runtime, obtain its domain, register the calling thread, load an assembly and invoke its entrypoint through embedding APIs, provided the game's exported functions and ABI allow it. The [Mono embedding guide](https://www.mono-project.com/docs/advanced/embedding/) documents thread registration and invocation. It also documents historical embedding ABI differences. This guide is about Mono generally, not a guarantee for Unity's fork. No second Mono initialization or cleanup should be inferred as necessary for an existing player.

An IL2CPP attachment route can instead call the existing native APIs directly, or host CoreCLR and initialize interop against the running IL2CPP runtime. Both require a new readiness/scheduling mechanism and correct shutdown handling; neither is established by the startup chainloader implementation. A native rendering hook without managed loading is another alternative, but it must independently establish scene/camera access and rendering lifetimes.

## Inspection and generated interop

Mono retains executable managed assemblies and runtime type information for retained code. Reflection or embedding calls can inspect classes and invoke retained methods. Exact assembly identity, framework profile and method availability matter. The inspected BepInEx Mono projects target `net35` and `netstandard2.0`, evidence that old and newer CLR profiles require explicit packaging consideration. [Project file](https://github.com/BepInEx/BepInEx/blob/5b766a3b7f6c164d4798924a93f3acf4db769d06/Runtimes/Unity/BepInEx.Unity.Mono/BepInEx.Unity.Mono.csproj).

IL2CPP does not execute an ordinary added C# assembly in its native game runtime. BepInEx's inspected IL2CPP project targets `net6.0`. Its [interop manager](https://github.com/BepInEx/BepInEx/blob/5b766a3b7f6c164d4798924a93f3acf4db769d06/Runtimes/Unity/BepInEx.Unity.IL2CPP/Il2CppInteropManager.cs) reads native game code and metadata through Cpp2IL, obtains matching Unity base assemblies, and generates CoreCLR interop assemblies. Configuration can use alternate or local base libraries. Generation and runtime initialization are separate steps, and failures remain possible at both steps. Its cache hash covers the game binary, base libraries, rename map and selected tool versions; an application cache design should separately state all inputs it intends to track, including metadata.

Interop's [native API declarations](https://github.com/BepInEx/Il2CppInterop/blob/81a6f78c8b653e0da4a3420ac4cd00819e8b6292/Il2CppInterop.Runtime/IL2CPP.cs) expose assembly enumeration, class methods and fields, invocation, internal-call resolution and thread registration. These declarations establish the mechanisms expected by this runtime, not that every game's binary exports them unchanged. Metadata enumeration lists retained types and methods. Live object discovery still needs Unity enumeration, an object registry or another runtime observation mechanism. Metadata does not itself identify the active gameplay camera.

Interop's [version handler](https://github.com/BepInEx/Il2CppInterop/blob/81a6f78c8b653e0da4a3420ac4cd00819e8b6292/Il2CppInterop.Runtime/Runtime/UnityVersionHandler.cs) selects versioned native structure adapters. It has explicit behavior changes at Unity 2018.1, 2021.2 and 2020.3.41. Those are code branch thresholds, not supported-version boundaries. Cpp2IL's release notes claim newer metadata support through Unity 6000.5 alpha, while an older core README still describes a smaller metadata range. Treat the installed parser, runtime adapters and exact player metadata as separate version inputs. Do not promote either documentation statement into a complete compatibility promise. [Cpp2IL release notes](https://github.com/SamboyCoding/Cpp2IL/releases/tag/2022.1.0-pre-release.21).

## Stripping and missing modules

Unity's [scripting restrictions](https://docs.unity.cn/Manual/ScriptingRestrictions.html) explain why reflection does not guarantee AOT code generation for an otherwise unused method or generic instantiation. CoreCLR can run the injector's own managed code, but that does not add an absent native game implementation.

Interop attempts to add absent Unity wrappers using matching reference assemblies. Its method restoration pass skips constructors and abstract methods, rejects unsupported signatures, restores eligible managed bodies through another pass, and generates delegates for internal calls. Its runtime's `ResolveICall` returns a delegate that throws when an internal call cannot be found. Thus generation can succeed while a later invocation still fails. [Restoration pass](https://github.com/BepInEx/Il2CppInterop/blob/81a6f78c8b653e0da4a3420ac4cd00819e8b6292/Il2CppInterop.Generator/Passes/Pass80UnstripMethods.cs), [internal-call resolution](https://github.com/BepInEx/Il2CppInterop/blob/81a6f78c8b653e0da4a3420ac4cd00819e8b6292/Il2CppInterop.Runtime/IL2CPP.cs).

A supplied reference DLL can provide a managed signature or eligible managed logic. It is not a replacement for removed native engine modules, an XR provider package, a render-pipeline implementation or missing shaders. Conversely, missing Unity XR support does not logically rule out an external native XR compositor route. These conclusions follow from the separation between managed bindings and native implementations; this investigation does not validate a replacement route in any stripped player.

## Thread and object lifetimes

BepInEx Mono's [ThreadingHelper](https://github.com/BepInEx/BepInEx/blob/5b766a3b7f6c164d4798924a93f3acf4db769d06/Runtimes/Unity/BepInEx.Unity.Mono/ThreadingHelper.cs) queues delegates and drains them in `Update`. Current Unity reference [SynchronizationContext](https://github.com/Unity-Technologies/UnityCsReference/blob/cf91ce104c595f52c14d0dea24f56b76c96cdc1a/Runtime/Export/Scripting/UnitySynchronizationContext.cs) likewise queues work for the player loop. These are scheduling examples, not interchangeable facilities across the old Mono and separate CoreCLR domains. In particular, an injector worker's .NET synchronization context is not automatically Unity's context.

Unity distinguishes a managed object wrapper from its native object's existence. Current [UnityEngine.Object bindings](https://github.com/Unity-Technologies/UnityCsReference/blob/cf91ce104c595f52c14d0dea24f56b76c96cdc1a/Runtime/Export/Scripting/UnityEngineObject.bindings.cs) implement null-like comparison for destroyed objects. Retaining a managed reference cannot keep a destroyed camera or graphics device usable.

Interop's [object wrapper source](https://github.com/BepInEx/Il2CppInterop/blob/81a6f78c8b653e0da4a3420ac4cd00819e8b6292/Il2CppInterop.Runtime/InteropTypes/Il2CppObjectBase.cs) creates an IL2CPP GC handle for ordinary wrappers, resolves its target when accessing the pointer and frees the handle in its finalizer. Its separate [injected-class documentation](https://github.com/BepInEx/Il2CppInterop/blob/81a6f78c8b653e0da4a3420ac4cd00819e8b6292/Documentation/Class-Injection.md) warns about cross-domain collection and reference loops. A lifetime policy needs to distinguish ordinary wrappers, injected classes and Unity native objects. That guide also limits which injected members and signatures IL2CPP reflection can see. Class injection is a mechanism to add a component, not unrestricted parity with all Unity C# semantics.

For graphics, Unity's [native rendering sample](https://github.com/Unity-Technologies/NativeRenderingPlugin/blob/522254181faf188efa8b50c3e3bf6fce720b26e4/PluginSource/source/RenderingPlugin.cpp) gets `IUnityGraphics` through `UnityPluginLoad`, registers device callbacks, handles an already-created device and releases device-specific state on shutdown. An arbitrary OS `LoadLibrary` call has no `IUnityInterfaces` argument and does not itself prove that Unity called `UnityPluginLoad`. Queued render callbacks also require the callback code and referenced resources to remain alive until the render thread has consumed them. That last requirement is an inference from deferred invocation and must become an explicit teardown experiment.

`Camera.Render` documents callbacks and prohibits rendering a camera recursively. Its API presence does not establish correct integration into every URP/HDRP package or custom pipeline. [Unity 6 camera documentation](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Camera.Render.html). Keep pipeline rendering decisions separate from bootstrap success.

## Alternatives to carry into the decision tickets

| Alternative | What existing source supplies | What still needs an experiment |
| --- | --- | --- |
| Doorstop and BepInEx startup, separate Mono and IL2CPP distributions | Early runtime loading, chainloader, plugin lifecycle and IL2CPP generation | Exact packaged versions; stripped-player failures; callback readiness; coexistence and recovery |
| Doorstop startup with a smaller UGEVR entrypoint | Runtime loading without adopting the whole plugin framework | Engine-ready detection, main-thread queue, diagnostics and dependency handling |
| Late native attachment plus Mono embedding or IL2CPP APIs/CoreCLR interop | Documented runtime entrypoints and interop components | Correct existing-runtime discovery, missed startup events, export/ABI variation, scheduling and safe detachment |
| Native graphics and engine hooks | A possible route when managed bindings are absent | Version-specific hook discovery, scene/camera semantics, resource synchronization and every graphics backend |

No alternative is selected here. Failure of one loader or API on one title does not establish general impossibility. A replacement needs positive evidence for the capability it claims, not only evidence that another route failed.

## Minimum falsifiable experiments

1. Build controlled Windows x64 players for an older Mono profile and a newer Mono profile. Record the engine version, loaded runtime, framework profile, assembly/module identities and packaged dependency hashes. Require three fresh startup launches, plugin initialization once per process, recurring update callbacks and an independently recorded main-thread identity. Then attempt late attachment after gameplay has begun. Record which readiness callbacks were already missed rather than replaying them by assumption.
2. Build at least two IL2CPP generations with different metadata/layout versions. For each, vary managed and engine stripping. Probe retained and deliberately omitted methods separately. Require metadata enumeration, successful invocation of a retained method, a known absent-call diagnostic, an injected component's recurring updates and scene-transition survival. Retain all parser/runtime/base-library versions. An interop generation log alone fails this experiment.
3. Test lifetime boundaries. Destroy the discovered camera, unload its scene, disable and recreate the helper, force managed and IL2CPP collections where available, then replace render targets. Require stale objects to be rejected and replacement objects rediscovered. Log original state restoration and reference/handle release. Do not infer GC safety from a short successful frame run.
4. For each available graphics path, record script and native callback thread IDs, Unity plugin registration, device identity and render-resource ownership. Queue work, stop the injector, and require outstanding work to finish or cancel before code/resources unload. Exercise device shutdown or recreation where reproducible. Test both Unity-registered plugin loading and arbitrary native DLL loading to establish which callbacks actually arrive.
5. Only after those probes, run the accepted initial gate in Firewatch and Outer Wilds with three fresh launches and 3-5 minutes of physical gameplay per game, covering menus, transitions, tracking, recentering and recovery. An automated Steam Frame testbench may drive and capture this gate once streamed-game launch support exists. Neither source research nor a synthetic HMD proves the physical gate.
6. Expand through the accepted 24 available core combinations and two unrelated non-VR games per claimed backend/pipeline family. Mark unsupported controlled combinations explicitly and retain failure evidence. Unity versions, stripping settings, package versions and launch mode are extra test dimensions rather than silently implied coverage within those 24 combinations.

These experiments supply evidence for architecture choices and compatibility claims. The report resolves factual preparation only. Bootstrap mode, required adapters, fallback policy and the user's final release thresholds remain human decisions.
