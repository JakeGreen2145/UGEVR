# UEVR interaction capability inventory

This report answers [What are UEVR input, locomotion, UI, and object-attachment capabilities?](https://github.com/JakeGreen2145/UGEVR/issues/3). UGEVR's agreed target is full capability parity, delivered in stages. These rows describe outcomes to target, not a promise that every Unity game can support every outcome.

Research date: 2026-10-13. The inspected official default-branch source snapshot is UEVR `4ee5c6b6162dee2291fc75f9dfc57667f6d45a2d`; official documentation is `fc19e66b7173f259f00d1feb5cf687b3f0a5131a`. Neither snapshot is assumed to be a stable release. No UEVR runtime or physical controller test was performed. Local clones supplied the full source; browser retrieval of the same GitHub tree URLs failed. Every source citation below is pinned to the inspected commit and line range.

Evidence grades are **S**, static source confirms the named code path or UI, and **D**, official documentation alone supports the claim. S does not establish cross-game reliability. SDK-dependent rows confirm the visible caller, not the unavailable current UESDK implementation behind its reflection and engine calls. A public RenderDoc UESDK mirror contains authentic historical SDK commit `491f973a78d6ffff557b4a9f41d45da42ce21580`, pinned by historical UEVR `1b1693e820413a8afb1fdfd8f9da43a19870042e`. It does not contain the current SDK pin and is not used to silently substitute current internals in this inventory.

The current UGEVR comparison uses [Injector.cs](https://github.com/JakeGreen2145/UGEVR/blob/f37758cd23213f78f6d3f3f35d66e6a26ee42c6a/src/Injector.cs#L106-L214). Gap **G0** means absent from this camera/render POC, which reads HMD pose and temporarily changes the selected camera. **G1** means partial: F9 resets the tracked origin/yaw, but there are no separate standing-height, horizon, or controller commands. **G2** means a camera-only positional head offset already exists, but does not move a player body or its collider. Acceptance criteria below are future UGEVR checks, not completed tests. “Fixture” means a deliberately instrumented non-VR Unity test scene; cross-game acceptance must also name real titles and supported backends.

Scope boundaries remain explicit. Runtime controller pose/action support does not imply optical hand tracking, finger animation, automatic interaction semantics, universal collision-aware hands, gesture reloads, melee damage or multiplayer compatibility. Those would be UGEVR extensions or game adapters unless another audited source establishes them. No teleport locomotion or automatic vignette system was found in the inspected named settings and input code. This bounded absence is not a claim about every plugin/profile in the UEVR ecosystem. Gamepad smooth turn continues through original game input; it is not evidence of an independent universal locomotion controller.

## Architecture questions for staged delivery

1. Which input contracts must the first stage support: XInput-only, Unity legacy Input, the newer Input System, or game controller methods? An XInput hook reaches only games that consume that API. A shared action model should remain separate from each delivery adapter.
2. How will UGEVR find a local player, aim owner, weapon muzzle and collision body? Unity has Transform/Component conventions but no guaranteed acknowledged pawn, control rotation or ProcessEvent equivalent. Profiles, reflected heuristics and explicit game adapters need separate confidence/error rules.
3. Which update phases own pose application, game aim, object transforms and restoration? The current POC changes a camera only for rendering. Permanent attachments must execute on the gameplay path that computes shots/collisions, with physics and animation ordering tested.
4. What is the persistent selector format for Mono, stripped IL2CPP, scene reload and respawn? Stable hierarchy/component paths can become ambiguous. Versioned selectors need type/name/relative-path constraints and a clear unresolved-state UI.
5. Should roomscale move CharacterController, Rigidbody or custom controllers first, and how are blocking collision, vertical motion and head/body reconciliation defined? Camera-only tracking is already demonstrated; body movement remains a separate capability.
6. Which UI systems get adapters first? Unity overlay/camera/world Canvas, legacy IMGUI and third-party custom renderers do not share one Slate substitution point. Injector laser interaction and game-UI laser interaction should have separate acceptance tests.
7. Which capabilities should be generic, profile-configured or explicitly game-specific? Full target parity can include authored profiles, as UEVR's attachments already depend on discovered game object identities. Generalization must not mean pretending semantic actions are universal.
8. What evidence closes a delivery stage? Use an instrumented non-VR Unity fixture plus named real games, physical HMD/controllers, pose/input traces, shot-origin/collision checks, reload persistence and recorded failure behavior. Simulated render-pose checks alone cannot establish interaction parity.
