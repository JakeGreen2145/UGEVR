# Windows launch and Steam Frame stream controls

Research date: 2026-10-13. Resolves [Which Windows game-launch and Steam Frame stream controls are evidenced for Frame Testbench?](https://github.com/JakeGreen2145/UGEVR/issues/23), a factual prerequisite for [How should game discovery, launch or attach, and conflict recovery work for users?](https://github.com/JakeGreen2145/UGEVR/issues/15).

## Finding

There is a documented route worth implementing and testing: after pairing and a successful initial connection, launch SteamVR on the Windows PC to request reconnection to its last wireless headset, then launch the selected game with UGEVR. Valve documents that reconnection behavior. A Steam launch request, a live process, a runtime scene and a headset image are separate observations. None alone proves that the intended game is streaming correctly. No runtime or hardware claim is established by this source investigation.

The existing Frame Testbench can observe and override the headset runtime but has no Windows game launcher or stream lifecycle tool. A Windows session controller can supply launch, injector handshake and host observations, while a stream backend supplies a request and separately reported connection evidence. Automatic peer selection and disconnection still need bounded implementation probes; the absence of a public control in the inspected sources does not establish impossibility.

## Evidence and scope

- Frame Testbench: [source at f999d3bb70de55efb6a01214108f08c6b5e4f776](https://github.com/JakeGreen2145/frame-testbench/tree/f999d3bb70de55efb6a01214108f08c6b5e4f776).
- Proposed host OpenVR calls: [Valve header at 0924064316de3effbcd1acf1e309182a2deb1c05](https://github.com/ValveSoftware/openvr/blob/0924064316de3effbcd1acf1e309182a2deb1c05/headers/openvr.h). Its interfaces include IVRApplications_008 and IVRCompositor_029. Probe interface availability in the installed runtime.
- Public Valve and Microsoft documentation below was read on the research date. These web pages are mutable, unlike pinned code.
- This work read local public-source clones and public documentation. It performed no SSH connection, headset access, game or SteamVR launch, install, pairing, setting change or configuration/secret inspection. It created no executable prototype.
- The Frame Testbench vendor client header is independently supplied. Its whole-file SHA-256 differs from the proposed Valve pin; this report does not claim they are identical or that a driver-header pin also pins the client SDK.

## Documented controls and their limits

| Operation | Evidence | What it establishes |
| --- | --- | --- |
| Launch a known Windows executable | Microsoft [CreateProcessW](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessw) accepts an executable, arguments, environment and working directory, and returns process identification/handles. It returns before initialization finishes. | A direct launcher can retain process identity and await exit. It needs a separate injector/game readiness handshake. |
| Request a Steam library launch | Valve [ISteamApps](https://partner.steamgames.com/doc/api/ISteamApps#GetLaunchCommandLine) documents steam://run/<appid> launch parameters. Valve's [API overview](https://partner.steamgames.com/doc/sdk/api#SteamAPI_RestartAppIfNecessary) says relaunch through Steam targets the installed library copy and may select a different executable. | A Steam launch request is evidenced. It does not select an arbitrary test copy, preserve a caller's environment, return the eventual game PID, or start a Frame stream by contract. |
| Open a URI through Windows | Microsoft [SHELLEXECUTEINFOW](https://learn.microsoft.com/en-us/windows/win32/api/shellapi/ns-shellapi-shellexecuteinfow) documents that a successful shell operation may return no process handle when an existing process handles the request. | Shell success must not be reported as game ready. Resolve the actual game through its injector handshake and process identity. |
| Launch/identify a registered OpenVR application | Valve's [IVRApplications](https://github.com/ValveSoftware/openvr/blob/0924064316de3effbcd1acf1e309182a2deb1c05/headers/openvr.h#L2743) provides manifests, LaunchApplication, IdentifyApplication, and application-key/PID lookup. LaunchApplication replaces the current scene app; PerformApplicationPrelaunchCheck can also make it quit. LaunchInternalProcess expects the caller to exit on success. | These are application lifecycle calls, not a remote stream-start API or harmless status checks. IdentifyApplication requires a known manifest. A launcher should not invoke destructive prelaunch checks while merely discovering state. |
| Connect or disconnect a Frame stream | Valve's [Steam Frame setup, Streaming](https://partner.steamgames.com/doc/steamhardware/steamframe/setup#Streaming) describes selecting the PC name in the headset dashboard to connect and selecting it again to disconnect. It states that PC-side SteamVR launch reconnects to the last wireless headset used. | This supports a PC reconnect probe after setup. It does not document programmatic selection of an arbitrary headset, reconnection guarantees after timeout, or a headless disconnect API. |
| Launch through the headset library | The same [Valve setup page](https://partner.steamgames.com/doc/steamhardware/steamframe/setup#Streaming) describes the normal Library Stream button separately from direct development streaming. | A user-facing launch route exists. No public typed automation API for that button was found in this bounded investigation. |
| Observe generic Steam Remote Play sessions | Valve [ISteamRemotePlay](https://partner.steamgames.com/doc/api/ISteamRemotePlay) exposes session counts/IDs, connected user SteamIDs and connection callbacks, plus Remote Play Together invitations/input functions. [Steamworks initialization](https://partner.steamgames.com/doc/sdk/api#SteamAPI_Init) requires a valid application context. | The documented interface has no general connect-to-Frame/disconnect method. A user SteamID is not a unique headset identity. Whether Frame VR direct streaming appears through this interface is unproved; it cannot be the required readiness signal without a probe. |

Setup is distinct from a test run. Valve's streaming instructions include adapter-driver installation, pairing with a headset code and account/context checks. Developer mode enables SSH and other development access. Those steps must be completed and verified separately; this research did not perform them. The per-run reconnect candidate assumes the intended paired headset is the last one used. If another wired headset or peer is selected, the controller must report the mismatch rather than silently count it as a Frame run. This last condition is an implementation requirement inferred from Valve's last-headset behavior, not an additional Valve API guarantee.

No unsupported steam://remoteplay, stream, or peer-selection URI is promoted to an API contract. Such candidates require their own observed, versioned probe. No broad private Steam protocol investigation is needed before trying the documented reconnect path.

## What Frame Testbench actually supplies

[MCP definitions](https://github.com/JakeGreen2145/frame-testbench/blob/f999d3bb70de55efb6a01214108f08c6b5e4f776/frame_testbench/mcp_server.py) expose one startup-configured target, status, pose/controller inputs, worn/compositor overrides, session operations, capture and recording. They expose no game launch, Windows process attachment, stream request, peer selection or stream stop. [CLI routing](https://github.com/JakeGreen2145/frame-testbench/blob/f999d3bb70de55efb6a01214108f08c6b5e4f776/frame_testbench/cli.py#L215) forwards commands to the headset; [SSH transport](https://github.com/JakeGreen2145/frame-testbench/blob/f999d3bb70de55efb6a01214108f08c6b5e4f776/frame_testbench/transport.py#L41) is command transport, not streaming control.

The [observer](https://github.com/JakeGreen2145/frame-testbench/blob/f999d3bb70de55efb6a01214108f08c6b5e4f776/native/observe.cpp#L135) reports headset/controller identity and poses, space transforms and compositor frame/timing/presentation data. It does not report the intended Windows game PID or stream peer/app identity. Host-side OpenVR observation can add GetCurrentSceneProcessId, GetCurrentSceneFocusProcess and GetLastFrameRenderer. The first can identify a scene before rendering; the last can be zero for compositor-rendered frames. These observations must stay local to their runtime host: a PID reported by a headset runtime is not automatically a Windows PID. These API meanings are in the [pinned Valve header](https://github.com/ValveSoftware/openvr/blob/0924064316de3effbcd1acf1e309182a2deb1c05/headers/openvr.h#L2869).

The [driver proxy](https://github.com/JakeGreen2145/frame-testbench/blob/f999d3bb70de55efb6a01214108f08c6b5e4f776/native/input_proxy.cpp#L35) wraps HMD driver callbacks, and [input state](https://github.com/JakeGreen2145/frame-testbench/blob/f999d3bb70de55efb6a01214108f08c6b5e4f776/native/input_state.cpp#L99) replaces HMD pose publication and publishes synthetic controller poses/input to that runtime. This proves the local mechanism in source. It does not prove that those overridden poses or synthetic controllers are forwarded into the PC streaming runtime. That path needs a causal test with host pose/action telemetry and resulting game images.

The [lease implementation](https://github.com/JakeGreen2145/frame-testbench/blob/f999d3bb70de55efb6a01214108f08c6b5e4f776/frame_testbench/session.py) uses a headset guard, a default 120-second lease and a maximum 300 seconds. Ending a session separately attempts override release and automatic compositor standby restoration. [MCP recording](https://github.com/JakeGreen2145/frame-testbench/blob/f999d3bb70de55efb6a01214108f08c6b5e4f776/frame_testbench/mcp_server.py#L300) limits each recording to 60 seconds; its default headset view is a left-eye texture recording. The extension must renew leases and compose bounded recordings across the agreed 3–5 minute gameplay interval. Ending this lease is not evidence that a PC game or wireless stream stopped.

## Smallest useful implementation probes

These are proposed falsifiable probes, not completed tests or a product-policy decision.

1. Record a known paired PC/headset selection and runtime versions during separate setup. From an idle state, request PC SteamVR launch through a verified installed entry point. Observe the intended headset connected with valid tracking on the host, plus the existing headset observer. Repeat after a clean disconnect. Retain timeout/wrong-device evidence. Do not infer success from a running SteamVR process.
2. Launch one existing non-VR test game through the direct executable path, with startup UGEVR configuration and a random run ID. Have the injector report that ID, its PID, executable/build identity, adapter/runtime/profile and first successful stereo submission. Match host runtime scene/render PID when available. A Steam route is a separate repeat of this probe because Steam may launch another installed executable.
3. Submit a small recognizable run marker in each eye. Capture host eye images and headset stereo screenshots, and verify marker/game content with a recorded time interval. A left-eye video alone does not prove both eyes. Advancing frame counters, a non-black screenshot or the appearance of the Steam dashboard cannot substitute for game association.
4. Under a renewed testbench lease, apply a bounded HMD translation/rotation sequence and one controller action. Check headset readback, PC-side pose/action receipt, and the intended game camera/action response. If synthetic controllers are not forwarded, record that limitation and separately test a host-side controlled-input provider; do not call local headset input readback an end-to-end pass.
5. Request injector disable/restoration and game exit, then request stream disconnect using an observed supported control. Verify game/injector, stream and headset override cleanup separately. Repeat with early game exit, connection loss and client cancellation. The documented dashboard disconnect can establish a reference result; unattended disconnect remains unproved until its control is observed. Do not use deprecated CompositorQuit as a general stream-stop contract or stop a runtime that the run did not own.

For directly owned processes, Microsoft [job objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects) can group child processes; breakaway and externally launched Steam games complicate ownership. A Steam client already running outside the controller is not automatically an owned process tree. Graceful injector restoration and ownership-aware game shutdown therefore need explicit results even if a process kill is available.

## Viable contract for the decision ticket

A candidate shared Windows session controller can expose launch/request/status/stop with an operation ID, run ID, deadlines, structured errors and cancellation. Split a host-launch provider from a Frame-stream provider. GUI, CLI and Frame Testbench can call the same controller without coupling headset SSH to arbitrary Windows shell commands.

Status should report independent fields for host process identity, injector handshake, runtime scene/submission, stream request state, selected peer evidence, headset image association and input-path verification. Include unknown/unavailable where no observation exists. A request accepted state must not advance automatically to stream ready. A stop result should record each cleanup attempt and what the operation owned or reused.

The first stream provider can test the documented preconfigured-peer reconnect path. Keep an explicit assisted setup/connect/disconnect route when automatic control is unavailable. Future typed controls or observed UI automation can replace that backend without changing game launch or evidence collection. This is an inferred feasible separation, not a claim that the testbench extension, streaming, peer identification, routing of overridden input, or unattended stop already works.

The prerequisite is answered: public controls justify a bounded implementation attempt, with clear unknowns and acceptance probes. It supplies no basis for declaring Unity injection or Frame streaming generally impossible.
