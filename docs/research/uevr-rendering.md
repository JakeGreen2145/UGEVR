# UEVR rendering, runtime, tracking, and compatibility inventory

Research for [What are UEVR rendering, runtime, tracking, and compatibility capabilities?](https://github.com/JakeGreen2145/UGEVR/issues/2), 2026-10-13. This is a capability target for UGEVR, with staged delivery. It is not a promise that every Unity title can support every capability.

## Evidence boundary

I inspected the default-branch UEVR source at `4ee5c6b6162dee2291fc75f9dfc57667f6d45a2d` and official documentation at `fc19e66b7173f259f00d1feb5cf687b3f0a5131a`. Neither snapshot is assumed to be a stable release. The current UESDK submodule revision could not be fetched publicly. The visible calling code establishes intended mechanisms, but I could not verify current SDK scanning, layout discovery, or native engine access implementations. A [public mirror contains historical UESDK source](https://github.com/elliotttate/UESDK-RenderDoc/tree/491f973a78d6ffff557b4a9f41d45da42ce21580), matching the SDK tree referenced by [UEVR's June revision](https://github.com/praydog/UEVR/tree/1b1693e820413a8afb1fdfd8f9da43a19870042e/dependencies/submodules/UESDK). That historical revision is not the SDK of this report's UEVR snapshot and does not establish current compatibility. I did not build or run UEVR. All UEVR runtime behavior and performance remain untested here.

Grades are `S`, a mechanism exists in inspected source; `D`, an upstream documentation claim only; and `U`, a declaration or diagnostic control whose operational effect is not established. `S` does not mean proven compatibility or measured performance.

UGEVR status is assessed against the [managed injector](https://github.com/JakeGreen2145/UGEVR/blob/f37758cd23213f78f6d3f3f35d66e6a26ee42c6a/src/Injector.cs#L49-L197) and [native bridge](https://github.com/JakeGreen2145/UGEVR/blob/f37758cd23213f78f6d3f3f35d66e6a26ee42c6a/src/RenderBridge.cpp#L80-L125). Its baseline is OpenVR, D3D11, two explicit `Camera.Render` calls, runtime projection tangents and eye offsets, a standing-space HMD pose, F8 pause and F9 recenter. It restores the original camera and refreshes native texture pointers after rendering. [Published validation](https://github.com/JakeGreen2145/UGEVR/blob/f37758cd23213f78f6d3f3f35d66e6a26ee42c6a/docs/validation.json) covers simulated HMD title scenes in Firewatch and Outer Wilds, not physical-headset gameplay. `Partial` below always means that limited baseline. `Absent` means no implementing code in these files, not impossible.

## Capability inventory

IDs are stable within this report. Unity equivalents are proposed observable outcomes, not claims that Unity offers the same engine interfaces.

[Stereo device hooks][stereo] | S. SDK discovery unavailable. The usual performance advantage is [documented][renderdocs], not measured. | Prefer a stereo-aware Unity rendering path where the shipped pipeline supports it. | Absent. Explicit camera rerenders are not native stereo. | Both eyes render the same simulation tick; animations, shadows and temporal histories remain correct in representative pipelines. |

Visual head motion does not by itself move the player capsule. | Render poses compose with gameplay camera motion without corrupting original state. | Partial. ## First-principles implications and staged experiments

The existing proof establishes one route to stereo output, not the architecture of all Unity support. Unity has built-in, URP, HDRP, custom scriptable pipelines and shipped runtime variants. The Unreal stereo interface strategy cannot simply transfer. The required common contract is eye view/projection, frame identity, GPU resource ownership, pose timing, depth convention, camera/UI selection and state restoration. Engine-specific adapters implement that contract.

A first delivery can harden R04/R06/R09/R10/R12/R13/R24 on physical-headset Mono gameplay. It should preserve the full target in this table. A second experiment must answer whether explicit camera rerendering supports temporal effects and camera stacks, or whether a native Unity stereo/render-loop integration is necessary for R01/R25/R26/R34. OpenXR and D3D12 are independently testable transports after the renderer contract stabilizes. Compatibility remedies, depth and spectator output need fixtures before broad game claims.

These are experiment suggestions, not accepted architecture decisions. AFR remains in the inventory for parity accounting, but shipping its known binocular time mismatch requires an explicit product decision.

## Unresolved architecture questions

1. Which Unity pipelines/builds can expose a stereo-aware render route without missing native XR providers? Which require explicit rerendering or native render-loop hooks?
2. Can two eye renders share simulation state while giving scripts, particles, command buffers, motion vectors and temporal histories correct per-eye semantics?
3. What native camera/render/GPU interface is common to Mono and IL2CPP, and how are unsupported builds detected before unsafe calls?
4. Where should pose sampling occur relative to Unity's main, render and GPU work, and how will texture/pose frame identity be verified independently?
5. What owns camera selection across camera stacks, weapon cameras, split-screen, cutscenes and render-texture views?
6. How can depth be acquired with correct reversed-Z, clip and unit metadata for each pipeline/runtime pair?
7. What minimum physical headset/runtime/gameplay matrix establishes a supported capability, and which compatibility settings justify a generic feature versus a per-title profile?
8. Should AFR be a user-facing emergency option, a diagnostic-only option, or an explicitly unsupported UEVR capability with a documented reason?
9. How do reset, disable and error paths restore Unity camera/gameplay/render settings and release GPU/runtime ownership?
