# UEVR platform capability inventory

Research question: [What are UEVR injector, profile, diagnostics, and extension capabilities?](https://github.com/JakeGreen2145/UGEVR/issues/4)

This inventory defines Unity outcomes for UGEVR's full capability target with staged delivery. It does not select an implementation or promise that every Unity game can support those outcomes. There are 45 stable capability IDs, P01 through P45. Exposed settings, actions and API groups appear in the coverage appendix.

## Evidence and scope

Inspected on 2026-10-13. These are pinned default-branch snapshots, not a claim about the stable UEVR release or the exact contents of a downloaded release:

- UEVR backend `4ee5c6b6162dee2291fc75f9dfc57667f6d45a2d`.
- UEVR frontend `dd6d372813097668a67e107c543f513d3170dc7a`.
- UEVR documentation `fc19e66b7173f259f00d1feb5cf687b3f0a5131a`.
- UGEVR runtime baseline `f37758cd23213f78f6d3f3f35d66e6a26ee42c6a`, before wayfinding documentation.

Every UEVR mechanism below has grade **S**, static source inspection, or **D**, documentation only. No UEVR runtime test was performed. Grade S proves that the inspected code implements a path, not that the path works in every game. Unreal reflection and version discovery often call UESDK. The exact current UESDK pin was unavailable publicly in this checkout, so its implementations and cross-version behavior remain unverified here. A public RenderDoc fork contains an authentic historical pin used by UEVR in June 2026; it is supplementary evidence, not the current SDK. The project provenance report will record that distinction. [The build instructions explain the EpicGames access requirement][B1].

Unity equivalents and acceptance criteria are proposed outcomes, not verified Unity implementation claims. The UGEVR baseline has BepInEx startup installation, managed Unity camera rendering and a native D3D11 OpenVR bridge. It logs camera selection, stages, submission errors and transforms, captures eye/compositor images, and has a simulated-headset tracking check. It has no product frontend, profile system, extension API, Lua runtime, OpenXR backend or general object explorer. This baseline is visible in [Injector.cs][U1], [RenderBridge.cpp][U2], [installation][U3] and [launch script][U4]. The existing two-game simulation is useful evidence for rendering, not evidence of platform parity. UEVR core source has an all-rights-reserved notice, while the public API/examples and some binding files carry separate licenses. This inventory describes behavior; it does not authorize copying core code. [B30]

## Coverage appendix

### Frontend settings and actions

P01-P22 cover `--attach=<exe>`, process selection/refresh, Inject, Terminate Connected Process, Restart as Admin, Focus Game on Injection, OpenVR/OpenXR choice, VR-plugin nullification, global/game directory buttons, Import Config and Export Config. Persisted frontend preference names are `OpenXRRadio`, `OpenVRRadio`, `NullifyVRPluginsCheckbox`, `IgnoreFutureVDWarnings` and `FocusGameOnInjection`. [F16]

Pre-injection keys are `VR_RenderingMethod`, `VR_SyncedSequentialMethod`, `VR_UncapFramerate`, `VR_Compatibility_SkipPostInitProperties` and the later frontend-selected `Frontend_RequestedRuntime`. `VR_RenderingMethod` exposes Native Stereo, Synced Sequential and Alternating/AFR. Sequential mode exposes Skip Tick and Skip Draw. These are covered as preflight configuration here; their rendering semantics belong in the rendering inventory. [F11][F5]

The frontend also links documentation, GitHub, donation and Flat2VR community pages. Those are navigation actions, not additional injection capabilities. [F18]

### Framework and diagnostic actions

P23-P29 cover the registered `FrameworkConfig` option suffixes `MenuKey`, `MenuOpen`, `RememberMenuState`, `EnableL3R3Toggle`, `L3R3LongPress`, `AlwaysShowCursor`, `AdvancedMode`, `ImGuiTheme`, `LogLevel`, `ShowCursorKey` and `FontSize`. Themes are Default Dark, Alternative Dark, Default Light and High Contrast. [B10]

Covered actions include save/reload/reset config, Attempt to reinitialize, Reinitialize Runtime, Display Console, Spawn Native Console, Dump All CVars and Clear Frozen CVars. Command console functionality includes search, variable display/set and command execution. `user_script.txt`, `cvars_standard.txt`, `cvars_data.txt` and `cvardump.json` are separate persisted files. [B4][B6][B12][B13][B14][B15]

The particular render/performance CVar names are engine settings, not a universal Unity command contract. The source list in `CVarManager.hpp` must be considered by the rendering report. Adding a command console to Unity does not manufacture the game's missing commands.

### Native ABI callbacks and API groups

P31-P36 cover all function-table groups in `API.h`. The exact member-name appendix below is generated from this pinned header, including SDK reflection, pose/controller/setting access and runtime interfaces. These are grouped capabilities, not hundreds of independent parity promises. Opaque handles and structures represent Unreal-specific types. The Unity target requires equivalent outcomes with Unity lifetime/coordinate rules.

Native callback groups include `on_present`, `on_device_reset`, `on_message`, `on_xinput_get_state`, `on_xinput_set_state`, `on_post_render_vr_framework_dx11`, `on_post_render_vr_framework_dx12`, `on_custom_event`, `on_pre_engine_tick`, `on_post_engine_tick`, `on_pre_slate_draw_window_render_thread`, `on_post_slate_draw_window_render_thread`, `on_early_calculate_stereo_view_offset`, `on_pre_calculate_stereo_view_offset`, `on_post_calculate_stereo_view_offset`, `on_pre_viewport_client_draw` and `on_post_viewport_client_draw`. [B16][B18]

`Plugin.hpp` provides `on_dllmain` and `on_initialize` plus most listed callbacks. Its virtual names for Slate callbacks are `on_pre_slate_draw_window` and `on_post_slate_draw_window`, without `_render_thread`. This helper does not expose the early-stereo virtual callback. The guide's advertised `on_frame`, `on_draw_ui`, `on_config_load` and `on_config_save` virtual functions are absent from this pinned `Plugin.hpp`; Lua does expose frame/UI callbacks. Do not treat that guide list as proven C++ helper parity. [B17][D2]

### Lua coverage

P37-P41 cover callbacks `on_xinput_get_state`, `on_xinput_set_state`, `on_pre_engine_tick`, `on_post_engine_tick`, `on_pre_slate_draw_window_render_thread`, `on_post_slate_draw_window_render_thread`, `on_early_calculate_stereo_view_offset`, `on_pre_calculate_stereo_view_offset`, `on_post_calculate_stereo_view_offset`, `on_pre_viewport_client_draw`, `on_post_viewport_client_draw`, `on_frame`, `on_draw_ui`, `on_script_reset` and `on_lua_event`. [B23]

Lua binds public C tables, `uevr.api`, `uevr.sdk.callbacks` and Unreal reflection types. Math types include Vector2/3/4, Quaternion, Rotator and Matrix4x4 in applicable float/double variants; XInput state/gamepad/vibration types are included. P34/P38 cover object arrays/items, UObject/UField/UStruct/UClass/UScriptStruct/UFunction, FField/FProperty/FFieldClass/FName, console manager/objects/variables/commands, viewport client and object-hook motion-controller state. Binding implementations, rather than generated docs alone, are the reference. [B23]

Additional named bindings are `imgui`, `json` and `fs`, and `uevr.lua.add_script_panel`. Lua-loader settings have suffixes `LogToDisk`, `GarbageCollectionHandler`, `GarbageCollectionType`, `GarbageCollectionMode`, `GarbageCollectionBudget`, `GarbageCollectionMinorMultiplier` and `GarbageCollectionMajorMultiplier`. Actions are Run script, Reset scripts, Spawn Debug Console and per-known-script enable toggles. [B8][B24][B25]

### Blueprint behavior and external projects

P42-P43 translate Blueprint support into engine-script/XR and tracked-component outcomes. Documented HMD functions are enabled/connected, device pose, orientation/position, motion-controller data, XR-system flags, HMD data and orientation/position resets. Controller data is explicitly left/right only, with Valid, Aim Position/Rotation and Grip Position/Rotation. Flags describe runtime, HMD/controllers, thumbrests, pitch and aiming mode. Documentation says activation and engine version affect which native hooks are used. This does not establish general Unity legacy-XR or XR Interaction Toolkit compatibility. [D1][B27]

Rai Pal, community compatibility databases, automatic community-profile downloads, UE4SS and UUU are external tools. The inspected UEVR frontend has local ZIP import/export and external navigation; it does not establish an owned online catalog, automatic profile discovery or one-click storefront library launcher. Do not inflate UEVR parity by crediting those ecosystem functions to its injector. UEVR's LuaVR bridge and Blueprint behavior are owned integration capabilities; UE4SS project generation is expressly external in the guide. [F14][F15][F18][B26][D1]

## Architecture questions left open

1. Which Unity attachment methods can support running-process injection versus startup installation across Mono and IL2CPP, without tying the frontend to one mod loader?
2. What is the stable game/profile identity, and how do engine/adapter changes invalidate a profile safely?
3. Which settings are live-safe, require session recreation or require a game restart? Which thread owns application of each setting?
4. Should the public extension contract start with a C ABI and managed wrappers, or managed adapters with a native bridge? How are handles invalidated on scene unload and domain/runtime changes?
5. Is Lua the preferred script language, or does another supported scripting mechanism provide equivalent authored behavior? How are callback budgets, native hooks and executable profile imports trusted?
6. Which Unity XR APIs should be populated, and which outcomes should use a UGEVR API? Literal Blueprint names are not the target.
7. How can clean runtime/graphics recovery be measured on physical headsets and multiple backends without reusing a stale native texture or object?
8. Which platform capabilities enter each delivery stage, and what fixture matrix proves the stage before broadening compatibility?
