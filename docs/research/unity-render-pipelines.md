# Stereo and capture in originally non-VR Unity players

Research date: 2026-10-13. This answers [Which stereo and capture facilities remain available in non-VR Built-in, URP, and HDRP players?](https://github.com/JakeGreen2145/UGEVR/issues/18). It supplies facts and falsifiable experiments for later architecture decisions. It does not select an architecture or claim compatibility with an untested player.

## Answer and evidence boundary

An ordinary desktop Unity player can retain enough scene rendering to produce two eye views without activating Unity XR. UGEVR already demonstrates this narrower mechanism in the simulated Firewatch and Outer Wilds runs. Public Unity APIs and pipeline source support further routes, but their presence, semantics and cost depend on the player build and pipeline version. This research ran no player, built no fixture and tested no physical headset. The existing proof remains a simulated Mono/D3D11/OpenVR result, as documented in the [UGEVR README](https://github.com/JakeGreen2145/UGEVR/blob/6f84686187025e1e9d2968f61d5713f0d006b905/README.md).

There are two especially useful corrections to broad assumptions:

- Unity's 2022.3 comparison lists `Camera.Render` as supported in Built-in, URP and HDRP. It lists several legacy camera callbacks and command-buffer attachment APIs as unsupported in SRP. A blanket statement that `Camera.Render` never works in SRP is therefore unsupported. A working camera render also does not imply that all original image effects, custom callbacks or camera compositions survive. [Unity 2022.3 comparison, render pipeline hooks](https://docs.unity3d.com/2022.3/Documentation/Manual/render-pipelines-feature-comparison.html#scripting)
- Modern render requests have a version boundary. URP 14 implements `StandardRequest` and `SingleCameraRequest`. Unity 2022.3 and 2023.1 document HDRP `StandardRequest` as unsupported. HDRP 16 source, associated with Unity 2023.2, implements it. Its separate request history is not automatically a separate history for each eye. [2022.3 StandardRequest](https://docs.unity3d.com/ja/2022.3/ScriptReference/Rendering.RenderPipeline.StandardRequest.html), [2023.1 StandardRequest](https://docs.unity3d.com/cn/2023.1/ScriptReference/Rendering.RenderPipeline.StandardRequest.html), [2023.2 StandardRequest](https://docs.unity3d.com/cn/2023.2/ScriptReference/Rendering.RenderPipeline.StandardRequest.html), [HDRP 16 implementation](https://github.com/Unity-Technologies/Graphics/blob/31f318449d59c2ca3942758a2fe9a0741f0dc914/Packages/com.unity.render-pipelines.high-definition/Runtime/RenderPipeline/HDRenderPipeline.cs#L2335)

No inspected fact proves that injecting VR generally into Unity is impossible. Missing XR support narrows available mechanisms in that artifact; it does not remove ordinary scene rendering. The amount of recovery work and the achievable fidelity remain empirical questions.

The repository provides C# wrappers rather than all native engine implementation, so a native binding's existence is not a proof of its runtime behavior in a particular UnityPlayer binary. These exact files establish versions; the branch names are not the version evidence. The linked manuals are version-specific documentation, not immutable snapshots of native engine code. Their URLs pin the documented release family. Source links pin the actual inspected commits. Neither substitutes for identifying the shipped game's editor, package, scripting backend and graphics device.

## Render mechanisms and their constraints

| Mechanism | Source-backed availability | What remains unproven in a shipped non-VR player |
| --- | --- | --- |
| `Camera.Render` into a `RenderTexture` | Built-in is established by the existing UGEVR prototype. Unity 2022.3 also documents it for URP and HDRP. It uses camera settings and cannot render the camera while it is already rendering. | Reachable binding, valid call point, original callbacks/effects, camera composition, eye histories and GPU cost. The existing old Mono successes do not establish newer SRP or IL2CPP support. |
| URP 14 `StandardRequest` | Source supports it and runs the pipeline render path. Documentation describes complete Base-camera stacks. | Request type and generic native call surviving stripping, exact renderer/custom-feature behavior, all stack cameras receiving the intended eye matrices. |
| URP 14 `SingleCameraRequest` | Source supports it, invokes camera/context events and renders the single camera. Its single-camera path rejects Overlay cameras. | Faithful capture of viewmodels and overlays. It intentionally does not establish complete-stack capture. |
| HDRP 14 render requests | The documented `StandardRequest` is unsupported; the base pipeline implementation returns false unless overridden. | Other routes remain possible. An unsupported request does not prove `Camera.Render`, camera target redirection, pipeline interception or native rendering cannot work. |
| HDRP 16 `StandardRequest` | Source accepts it, disables AOV requests during capture, renders into the destination, and uses `CustomUserHistory0`. | Separate eye histories, preservation of custom AOV/compositor outputs, package-specific frame settings and upscalers. |
| Normal camera target redirection | Camera targets and pipeline rendering already exist for desktop gameplay. | Redirecting the first view alone produces a monoscopic image. A second real scene render, native stereo route or other geometry-aware mechanism is necessary for stereo. |
| Unity XR native display provider | Unity documents provider-defined view/projection matrices, culling/render passes, targets and graphics-thread submission. | Loader/provider deployment and registration in an already-built desktop player; XR engine code, SRP paths and shader variants must exist or need an independently validated recovery method. |
| Native graphics capture/interception | Unity supports render-thread native plug-in events and native texture access. | A desktop Present hook sees final pixels, not a second eye's occluded geometry. General stereo reconstruction needs deeper scene/draw interception or engine cooperation. No such universal native route was validated here. |

The table draws on [Camera.Render](https://docs.unity3d.com/2022.3/Documentation/ScriptReference/Camera.Render.html), [URP 14 request implementation](https://github.com/Unity-Technologies/Graphics/blob/03ca85dffdde4b7bc1d6870074e6f5ff9f0352a3/Packages/com.unity.render-pipelines.universal/Runtime/UniversalRenderPipeline.cs#L420), [HDRP 16 request implementation](https://github.com/Unity-Technologies/Graphics/blob/31f318449d59c2ca3942758a2fe9a0741f0dc914/Packages/com.unity.render-pipelines.high-definition/Runtime/RenderPipeline/HDRenderPipeline.cs#L2354), [XR display provider contract](https://docs.unity3d.com/2022.3/Documentation/Manual/xrsdk-display.html) and [native plug-in interface](https://docs.unity3d.com/2022.3/Documentation/Manual/NativePluginInterface.html). The unresolved cells are inferences and experiment requirements, not claims of failure.

### Disabled XR differs from missing XR

XR Management 4.0.7 documents manual `InitializeLoader`, `StartSubsystems`, `StopSubsystems` and `DeinitializeLoader` for a project that already contains configured loaders. That shows disabled automatic startup can be reversible. It does not show that invoking the same functions installs an absent provider in a shipped game. [XR Management lifecycle](https://docs.unity3d.com/Packages/com.unity.xr.management@4.0/manual/EndUser.html)

SRP Core 14 `XRSystem` enumerates display subsystem instances and considers the display active only when the selected subsystem is running. Its device discovery and layout creation depend on `ENABLE_VR && ENABLE_XR_MODULE`. Layout generation queries actual subsystem render parameters and culling parameters. Merely assigning stereo camera matrices does not satisfy these prerequisites. [XRSystem 14](https://github.com/Unity-Technologies/Graphics/blob/03ca85dffdde4b7bc1d6870074e6f5ff9f0352a3/Packages/com.unity.render-pipelines.core/Runtime/XR/XRSystem.cs#L46), [device discovery and pass construction](https://github.com/Unity-Technologies/Graphics/blob/03ca85dffdde4b7bc1d6870074e6f5ff9f0352a3/Packages/com.unity.render-pipelines.core/Runtime/XR/XRSystem.cs#L260)

An artifact probe should distinguish these cases:

1. XR code and a configured provider exist, but startup is disabled.
2. The XR module exists, but no suitable loader, native provider or subsystem descriptor is present.
3. The pipeline's compiled XR branches, managed methods or required shader variants are absent.
4. Required native engine entry points or modules are absent or version-incompatible.

Unity documents build-time managed stripping, reflection limitations and IL2CPP compilation. A source method or metadata name can exist without a callable retained implementation or usable generic instantiation. Build-time preservation annotations cannot retroactively restore a compiled method to an existing player. Injecting a matching managed library may help a Mono case, but it does not by itself restore native engine functions, compiled shader variants or IL2CPP machine code. These last distinctions follow from the build processes and require artifact inspection. [Managed stripping](https://docs.unity3d.com/2022.3/Documentation/Manual/ManagedCodeStripping.html), [IL2CPP process](https://docs.unity3d.com/2022.3/Documentation/Manual/IL2CPP.html), [shader variants](https://docs.unity3d.com/2022.3/Documentation/Manual/shader-variants.html)

### Rendering again differs from advancing gameplay again

Unity's execution-order documentation separates frame updates, physics steps and rendering callbacks. A render request processes rendering rather than explicitly invoking the game's full PlayerLoop. However, extra rendering can invoke original render callbacks and custom pipeline features. Those scripts may mutate gameplay or global render state. Therefore "one gameplay update, two eye renders" is an invariant to measure, not something to infer from two successful images. [Execution order](https://docs.unity3d.com/2022.3/Documentation/Manual/ExecutionOrder.html), [Camera.Render callback contract](https://docs.unity3d.com/2022.3/Documentation/ScriptReference/Camera.Render.html)

Simulation tick rate and HMD render cadence can differ. An end-of-frame eye pair ordinarily reuses one simulation state; it does not automatically introduce a higher-rate independent render loop. Unity's native XR contract puts pose-dependent frame cadence and submission on the graphics thread. A plug-in wait at the wrong point can stall the producer or add stale-pose latency. Establishing a different simulation/render schedule needs explicit measurement of frame IDs, physics ticks, pose timestamps and GPU completion. [XR frame lifecycle and cadence](https://docs.unity3d.com/2022.3/Documentation/Manual/xrsdk-display.html#frame-lifecycle)

### Temporal effects and culling need eye-aware state

HDRP 14 keys `HDCamera` by the camera object and XR multipass ID. Its update path advances `cameraFrameCount` per rendering, and its histories cover several temporal effects. Changing a non-XR camera between eyes without changing that key can reuse histories across incompatible viewpoints. HDRP 16 adds a history-channel key. Its user-request implementation always selects `CustomUserHistory0`, so two requests on the same camera and XR pass still share a request history. Separation from the ordinary render-loop history is not proof of left/right separation. [HDRP 14 HDCamera](https://github.com/Unity-Technologies/Graphics/blob/03ca85dffdde4b7bc1d6870074e6f5ff9f0352a3/Packages/com.unity.render-pipelines.high-definition/Runtime/RenderPipeline/Camera/HDCamera.cs#L139), [HDRP 16 HDCamera keys](https://github.com/Unity-Technologies/Graphics/blob/31f318449d59c2ca3942758a2fe9a0741f0dc914/Packages/com.unity.render-pipelines.high-definition/Runtime/RenderPipeline/Camera/HDCamera.cs#L137)

URP 14 explicitly updates camera motion-vector persistent data and TAA targets before culling. It obtains fresh culling results through `context.Cull`. This shows ordinary rerendering is more than copying color pixels. It does not prove that changing the same camera's eye matrices preserves correct temporal data. Separate camera identities, eye-specific state interception, native stereo or temporarily disabling affected temporal features are competing experiment routes, with fidelity and performance costs still to measure. [URP 14 rendering and histories](https://github.com/Unity-Technologies/Graphics/blob/03ca85dffdde4b7bc1d6870074e6f5ff9f0352a3/Packages/com.unity.render-pipelines.universal/Runtime/UniversalRenderPipeline.cs#L651)

For custom culling, occlusion, reflections, shadows and screen-space effects, a second eye requires the intended view and projection before culling and the intended state through the draw passes. A compositor warp or final-buffer copy cannot reveal geometry absent from the original view. This is a geometric inference, not evidence that a lower-level stereo route is impossible. TAA, temporal upscaling and dynamic resolution should each be checked with independent eye histories and stable resource dimensions rather than judged from a static scene.

### Camera stacks, viewmodels and UI are separate capture obligations

A Base camera is often only part of the displayed result. URP's stack route iterates valid overlay cameras, whereas its standalone path skips Overlay cameras. Changing only the Base camera may leave a weapon or UI camera with desktop projection. Cloning a Camera through `CopyFrom` copies camera settings; it does not establish that arbitrary game components, pipeline additional data or external camera-controller references have been duplicated. All of those are title-specific unknowns. [URP 14 camera stack](https://github.com/Unity-Technologies/Graphics/blob/03ca85dffdde4b7bc1d6870074e6f5ff9f0352a3/Packages/com.unity.render-pipelines.universal/Runtime/UniversalRenderPipeline.cs#L712), [Camera.CopyFrom](https://docs.unity3d.com/2022.3/Documentation/ScriptReference/Camera.CopyFrom.html)

Unity documents Screen Space Overlay Canvas rendering independently of any scene camera. A camera's eye RenderTexture therefore cannot be presumed to include it. Camera-space and world-space canvases have different placement and occlusion behavior. Changing Canvas mode, capturing UI separately or compositing an overlay are possible mechanisms, but require testing interaction, scaling, sorting and restoration. IMGUI and UI Toolkit also need identification; this Canvas evidence only establishes uGUI semantics. [Canvas modes](https://docs.unity3d.com/2022.3/Documentation/Manual/class-Canvas.html)

### End-of-frame and render-thread events have different jobs

`WaitForEndOfFrame` runs after cameras and GUI render, before display. It is a scheduling point, not proof that a particular eye texture contains all cameras or GUI. `RenderPipelineManager` camera/context events occur when the pipeline invokes them. An injected callback that submits more render requests needs a recursion guard and its own eye-pair identity; a context-end event is not necessarily the end of the whole application frame. [WaitForEndOfFrame](https://docs.unity3d.com/2022.3/Documentation/ScriptReference/WaitForEndOfFrame.html), [RenderPipelineManager event dispatch](https://github.com/Unity-Technologies/UnityCsReference/blob/91471827ee2cab002d877b827d67d120c09ba9d5/Runtime/Export/RenderPipeline/RenderPipelineManager.cs#L34), [URP 14 request event dispatch](https://github.com/Unity-Technologies/Graphics/blob/03ca85dffdde4b7bc1d6870074e6f5ff9f0352a3/Packages/com.unity.render-pipelines.universal/Runtime/UniversalRenderPipeline.cs#L482)

`GL.IssuePluginEvent` schedules a native callback on the render thread. Texture native pointers are graphics-API-specific, and `GetNativeTexturePtr` can synchronize with that thread. Unity documents pointer changes after texture modification. The current UGEVR refresh of eye pointers is an empirically useful workaround for its tested path; replacing it with cached pointers requires correct resource-lifetime and completion handling. D3D12 additionally needs the appropriate command queue, resource states and synchronization; a D3D11 success does not establish that path. Microsoft documents application-managed resource barriers and queue synchronization. [D3D12 resource barriers](https://learn.microsoft.com/en-us/windows/win32/direct3d12/using-resource-barriers-to-synchronize-resource-states-in-direct3d-12), [D3D12 queue synchronization](https://learn.microsoft.com/en-us/windows/win32/direct3d12/executing-and-synchronizing-command-lists) [Native plug-in events](https://docs.unity3d.com/2022.3/Documentation/Manual/NativePluginInterface.html), [GetNativeTexturePtr](https://docs.unity3d.com/2022.3/Documentation/ScriptReference/Texture.GetNativeTexturePtr.html)

## Smallest experiments that can reject candidate mechanisms

Each experiment must operate on a baseline desktop player built without UGEVR integration. Freeze its source revision, package lock, editor version, backend, graphics API and executable hashes before injection. A controlled sample confirms a controlled combination, not unrelated-game generalization. The separate fixture research identified Protoland, Boat Attack and Spaceship Demo as candidates; none was built or validated there. Boat Attack's URP 10.7 and Spaceship's HDRP 14.0.6 require exact-version probing rather than substituting the source versions inspected above.

| Candidate experiment | Smallest useful observation | What falsifies the proposed route for that build |
| --- | --- | --- |
| Discover retained rendering facilities | Log active pipeline/package version, Camera bindings, request types, callable generic path, XR subsystem descriptors and native module inventory. | Required method, instantiation, module or provider is absent, or invocation fails. Record the specific absence; do not label all Unity players impossible. |
| Manual two-eye Camera.Render | In each pipeline, render a moving asymmetric scene and edge-visible geometry into separate eye textures from HMD matrices at a nonrecursive call point. Restore every modified camera field after each pair. | No distinct views, missing expected scene passes, wrong culling, effects missing, unrecoverable camera state or unacceptable timing. A failure triggers examination of requests or pipeline interception. |
| URP render requests | Probe `SupportsRenderRequest`, compare Standard and SingleCamera outputs with the ordinary desktop output, including a weapon Overlay camera and custom renderer feature. | Unsupported/stripped path, missing composition, repeated callback side effects, or camera state changed after capture. |
| HDRP 14 versus 16 requests | Probe exact artifact support. On 16, compare same-camera requests against independent eye camera/state arrangements using TAA and moving occluders. | HDRP 14 rejection disproves that request route for that build. On 16, cross-eye ghosting rejects the assumption that request history is eye-isolated. It does not reject all HDRP routes. |
| Native XR revival | Start an existing retained loader first. Separately test runtime provider registration only in a desktop build known to retain required engine and shader support. | No running display/render passes, invalid targets, mono fallback or missing stereo variants. Avoid interpreting a source-integrated provider build as proof of post-build injection. |
| Simulation and callbacks | Count Update/FixedUpdate, render callbacks, custom passes and game-state changes per eye pair while logging pose/frame IDs. | Extra gameplay advancement, callback mutations, invalid event ordering or stale poses reject the scheduling arrangement. |
| Histories, upscaling and culling | Move objects/head through frustum edges; toggle TAA, temporal upscaler and dynamic resolution; inspect each eye's motion vectors and history isolation. | Cross-eye history, wrong occlusion, changing resource reuse, or unstable resolution rejects the mechanism or identifies a scoped feature limitation. |
| UI and multicamera capture | Capture world, viewmodel, camera-space HUD, Overlay Canvas and menu transitions. Check click/selection alignment and desktop restoration. | Missing layers, flat/inconsistent projection, duplicated UI, unusable interaction or damaged original camera state. |
| Native submission | Place render-thread markers after both eyes; measure GPU resource completion, pointer generation, runtime submission and frame age separately on D3D11 and D3D12. | Submission before completion, stale resources, incorrect states or queue waits, repeated/old frames or reset failure. |

Automated physical-headset checks through the Steam Frame testbench are a planned validation aid. Extending it to launch streamed games remains work, not evidence delivered by this research. The agreed first physical gate is 3 to 5 minutes of gameplay per game with fresh launches and the selected lifecycle checks. Longer-duration stability remains a later gate. The eventual 24 available core combinations and two unrelated non-VR titles per claimed backend/pipeline family remain broader obligations; this source audit passes none of them.

## What this resolves and what stays open

The factual question is resolved enough to inform the decision tickets: use version and artifact capability probing, retain ordinary scene rendering as a viable candidate outside Unity XR, and treat render requests, native XR and lower-level interception as distinct mechanisms with different prerequisites. HDRP 14 request absence and HDRP 16 history sharing are concrete constraints. They should appear in prototypes and acceptance checks.

The user still needs to choose the architecture, acceptable fidelity fallbacks and supported-version progression. Engineers still need to validate mechanism prototypes in real builds, determine stripped-player recovery, measure performance and run physical gameplay. No library, callback or current API documentation cited here establishes universal injectable availability, and no simulated success establishes full physical-headset gameplay or UEVR capability parity.
